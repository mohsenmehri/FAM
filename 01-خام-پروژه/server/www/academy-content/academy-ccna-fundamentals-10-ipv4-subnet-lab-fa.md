# CCNA NF-10 — IPv4 Subnetting و کاربرگ پیکربندی رابط

**سطح:** CCNA. **پیش‌نیاز:** NF-09. **هدف مرتبط:** CCNA v1.1 `1.6` Configure and verify IPv4 addressing and subnetting. **بازبینی متنی ۲۰۲۶-۱۱-۲۰:** روش Subnetting و طرح پیکربندی/Verification بازخوانی شدند؛ به‌علت فعل عملی، کفایت نهایی تا اجرای IOS/Image و ثبت نتیجه باز است. **وضعیت:** پیکربندی، خروجی و کاربرگ طراحی‌شده و اجرا‌نشده؛ ایمیج، مدل، نسخه و نام رابط تأیید نشده‌اند. این درس به‌تنهایی شاهد تأیید کامل هدف نیست.

## هدف

از روی Prefix، اندازهٔ Subnet، محدوده، Network و Broadcast مثال را محاسبه کنید؛ آدرس یک رابط IOS را در سناریوی مستقل طراحی کنید و با Verification و آزمون اتصال تفسیر کنید.

## ۱. روش Subnetting با مثال

برای `192.0.2.64/27`، تعداد بیت‌های Host برابر `32 - 27 = 5` است. اندازهٔ بلوک برابر `2^5 = 32` آدرس است. مضرب‌های ۳۲ در Octet آخر: ۰، ۳۲، ۶۴، ۹۶ و غیره. بنابراین:

| مورد | مقدار |
|---|---|
| Network | `192.0.2.64` |
| Mask | `255.255.255.224` |
| Broadcast | `192.0.2.95` |
| بازهٔ Host معمول | `192.0.2.65–192.0.2.94` |
| تعداد Host معمول | ۳۰ |

کم‌کردن ۲ از تعداد آدرس‌ها برای Subnet معمول میزبان‌دار این درس است؛ `/31` در لینک‌های Point-to-Point و `/32` برای یک Host/Route قواعد و کاربرد خاص دارند. `192.0.2.0/24` بازهٔ مستنداتی است، نه RFC 1918.

### روش عمومی برای Prefixهای مختلف

1. Prefix را به Mask تبدیل کنید: هر ۸ بیت کامل یک Octet برابر 255 می‌دهد؛ باقی‌ماندهٔ بیت‌ها در Octet بعدی `128, 192, 224, 240, 248, 252, 254, 255` می‌سازند.
2. از چپ، نخستین Octet ماسک که 255 نیست را پیدا کنید؛ اندازهٔ بلوک در آن `256 − مقدار Mask` است. اگر ماسک آن Octet صفر است، گام 256 یعنی در آن Octet فقط یک بلوک داریم؛ `/32` یک Host Route و حالت ویژه است.
3. مضرب‌های اندازهٔ بلوک را بنویسید؛ آدرس IP در کدام بازه افتاده، Network و Broadcast آن را مشخص می‌کند. Host معمول از Network+1 تا Broadcast−1 است (جز استثناها).

| مثال | Mask | Octet جالب / گام | Network | Broadcast |
|---|---|---|---|---|
| `192.0.2.70/27` | `255.255.255.224` | چهارم، `256−224=32` | `192.0.2.64` | `192.0.2.95` |
| `172.16.53.7/20` | `255.255.240.0` | سوم، `256−240=16`؛ بلوک `48–63` | `172.16.48.0` | `172.16.63.255` |

اگر میزبان `192.0.2.70/27` باشد، در بلوک `64–95` قرار می‌گیرد. `192.0.2.100/27` در بلوک بعدی `96–127` است، نه همان Subnet.

### انتخاب Prefix از تعداد Hostها (VLSM مقدماتی)

برای یک LAN سنتی، کوچک‌ترین بلوک را پیدا کنید که دست‌کم `تعداد Host + 2` آدرس داشته باشد، سپس Prefix متناظر را انتخاب کنید. نمونه: 50 Host به 64 آدرس نیاز دارد (`2^6`)، پس `/26` با 62 Host معمول جواب می‌دهد؛ `/27` فقط 30 Host معمول دارد و کافی نیست. برای چند LAN، معمولاً بلوک بزرگ‌تر را اول از فضای مادر جدا کنید تا فضای باقی‌مانده به مرزهای معتبر و بدون هم‌پوشانی تقسیم شود. این قاعده برای `/31` و `/32` و بعضی طراحی‌های خاص مستثناست.

## ۲. کاربرگ مستقل PNETLab — تقسیم یک بلوک به دو Subnet

**هدف رسمی `1.6`:** محاسبه، پیکربندی و Verification آدرس IPv4 و Prefix. **این آزمایش طراحی‌شده و اجرا‌نشده است.** یک Router IOS با دو رابط Ethernet، دو Switch داخلی مجزا و دو Client نوع VPCS کافی است؛ هر دو LAN فقط از طریق R1 به هم می‌رسند و هیچ اتصال بیرونی ندارند.

```text
PC-A 192.0.2.10/27 ─ SW-A ─ R1 Gi0/0 192.0.2.1/27
                                    R1 Gi0/1 192.0.2.33/27 ─ SW-B ─ PC-B 192.0.2.40/27
                                      بلوک مادر: 192.0.2.0/26
                                      LAN-A: 192.0.2.0/27 · LAN-B: 192.0.2.32/27
```

| گره/رابط | Address/Mask | Gateway | نقش |
|---|---|---|---|
| R1 Gi0/0 | `192.0.2.1/27` (`255.255.255.224`) | — | Gateway شبکهٔ A |
| PC-A | `192.0.2.10/27` | `192.0.2.1` | Client شبکهٔ A |
| R1 Gi0/1 | `192.0.2.33/27` (`255.255.255.224`) | — | Gateway شبکهٔ B |
| PC-B | `192.0.2.40/27` | `192.0.2.33` | Client شبکهٔ B |

دو `/27` از Parent `/26` به‌دست می‌آیند: A از `.0` تا `.31` (Usable معمول `.1–.30`) و B از `.32` تا `.63` (Usable معمول `.33–.62`). پیش از اجرا، نام/تعداد Interface، نسخهٔ IOS، قابلیت VPCS، Snapshot و ایزوله بودن Nodeها را ثبت کنید. `/31` و `/32` قواعد/کاربرد متفاوت دارند و در این محاسبهٔ LAN به‌کار نمی‌روند.

## ۳. پیکربندی پیشنهادی

**فرمان‌ها نمونه و اجرا‌نشده‌اند؛ با IOS/Client واقعی تطبیق دهید.** روی R1:

```text
configure terminal
interface GigabitEthernet0/0
 ip address 192.0.2.1 255.255.255.224
 no shutdown
interface GigabitEthernet0/1
 ip address 192.0.2.33 255.255.255.224
 no shutdown
end
```

روی دو VPCS، در صورتی‌که syntax نسخه همان باشد:

```text
PC-A> ip 192.0.2.10/27 192.0.2.1
PC-B> ip 192.0.2.40/27 192.0.2.33
```

Router IOS مسیرهای Connected را برای دو Interface می‌سازد؛ این مثال Static Route یا Dynamic Routing لازم ندارد. اگر به‌جای Router از Layer-3 Switch استفاده می‌کنید، نیاز به فعال‌کردن `ip routing` و SVI/پورت Routed را از مستند آن پلتفرم بررسی کنید؛ توپولوژی و CLI آن با این مثال یکسان نیست.

## ۴. Verification و نتیجهٔ مورد انتظار

**فرمان و خروجی آموزشی، نه Capture واقعی:**

```text
R1# show ip interface brief
GigabitEthernet0/0  192.0.2.1   YES manual up up
GigabitEthernet0/1  192.0.2.33  YES manual up up

R1# show ip route connected
C 192.0.2.0/27 is directly connected, GigabitEthernet0/0
C 192.0.2.32/27 is directly connected, GigabitEthernet0/1
```

روی هر PC، آدرس/Prefix/Gateway را از ابزار Client بررسی کنید؛ از PC-A، Gateway `.1`، PC-B و از PC-B، Gateway `.33` و PC-A را Ping کنید. انتظار طراحی‌شده: هر Client Gateway محلی و پس از آن Client دیگر را می‌بیند. موفقیت ICMP به‌تنهایی صحت همهٔ برنامه‌ها را ثابت نمی‌کند. خروجی `show ip route connected` در برخی نسخه‌ها Local `/32` و قالب متفاوت هم نشان می‌دهد.

## ۵. عیب‌یابی، نقص کنترل‌شده و بازگشت

| نشانه | بررسی مرحله‌ای |
|---|---|
| Interface `administratively down` | حالت پیکربندی و مجوز؛ `no shutdown` فقط در لاب |
| Interface `down/down` | Node/کابل مجازی، پورت و وضعیت سمت مقابل |
| PC-A به Gateway نمی‌رسد | Address/Prefix، LAN-A، Gateway R1 و link |
| دو LAN در `show ip route` نیستند | IP/Mask روی Interface، `no shutdown` و up/up |
| PC-A با PC-B ارتباط ندارد | دو Prefix متفاوت، Gateway هر Client و مسیر Connected R1 را بررسی کنید |

**نقص کنترل‌شده:** فقط روی PC-B Prefix را موقتاً `/26` کنید و کوشش کنید به PC-A برسید. با `/26`، PC-B ممکن است PC-A را Local تصور و به‌جای Gateway روی SW-B، ARP کند؛ چون PC-A پشت SW-A است، این آزمون باید شکست بخورد یا رفتار متفاوتی در Client نمایش دهد. Prefix را به `/27` برگردانید و Pingها را دوباره بگیرید. علت را با آدرس‌نامه/مسیر اثبات کنید، نه فقط با timeout.

**بازگشت:** از Snapshot استفاده کنید یا مقادیر اصلی Interface و VPCS را برگردانید؛ Config را در دستگاه عملیاتی دستکاری نکنید. **معیار موفقیت:** هر دو LAN از Parent `/26` درست استخراج شده‌اند، چهار آدرس در بازهٔ قابل استفاده قرار دارند، R1 دو Connected Route دارد، هر PC Gateway همان Subnet را دارد، آزمون ارتباط محلی/بین‌شبکه‌ای و نقص Mask ثبت و بازیابی شده‌اند. هیچ اجرای واقعی در این نسخه ثبت نشده است.

## ۶. سؤال‌های سناریویی و پاسخ

1. **`/27` چند بیت Host دارد؟** پنج بیت.
2. **بلوک `/27` چند آدرس دارد؟** ۳۲ آدرس، شامل Network و Broadcast در مثال معمول.
3. **Network آدرس `192.0.2.70/27` چیست؟** `192.0.2.64`.
4. **Broadcast آن چیست؟** `192.0.2.95`.
5. **آیا `192.0.2.100/27` در همان Subnet است؟** خیر؛ در بلوک `96–127` قرار می‌گیرد.
6. **آیا هر Subnet همیشه دو آدرس غیرقابل استفاده دارد؟** خیر؛ `/31` و `/32` کاربرد متفاوت دارند.
7. **`ip address` چه می‌کند؟** آدرس و ماسک را در رابط انتخاب‌شده تنظیم می‌کند، در صورت پشتیبانی پلتفرم.
8. **`no shutdown` چه می‌کند؟** رابط را از حالت اداری Shutdown خارج می‌کند؛ اتصال فیزیکی موفق را تضمین نمی‌کند.
9. **علامت C در خروجی نمونه چیست؟** مسیر شبکهٔ Connected در قالب معمول IOS.
10. **Ping ناموفق چه علت قطعی دارد؟** از این مشاهده مشخص نیست؛ رابط، آدرس، مسیر و مقصد بررسی شوند.
11. **آیا آدرس مستنداتی برای اینترنت واقعی طراحی شده است؟** خیر؛ این مثال برای مستندسازی است.
12. **آیا کاربرگ در PNETLab اجرا شده؟** خیر، تصویر و نتیجهٔ واقعی ثبت نشده است.

## واژه‌نامه و چک‌لیست

Subnet: زیرشبکه؛ Prefix: طول بیت شبکه؛ Broadcast: آدرس همه‌پخشی در مثال معمول؛ Connected Route: مسیر شبکهٔ متصل.

- [ ] بلوک `/27` را محاسبه می‌کنم.
- [ ] آدرس و ماسک دو سمت را بررسی می‌کنم.
- [ ] دستور و خروجی پیشنهادی را با اجرای واقعی اشتباه نمی‌گیرم.
