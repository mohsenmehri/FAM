# CCNA AUT-08 — Ansible، Terraform و ابزارهای مدیریت پیکربندی

**سطح:** CCNA. **پیش‌نیاز:** AUT-01. **هدف رسمی:** `6.6` تشخیص قابلیت‌های ابزارهای مدیریت پیکربندی مانند Ansible و Terraform؛ این درس قابلیت‌های معمول و محدودیت‌ها را مقایسه می‌کند، نه اینکه یک ابزار را برای همهٔ شبکه‌ها برتر بداند. **وضعیت:** پیش‌نویس محتوایی؛ سناریو طراحی‌شده و **اجرا‌نشده**؛ هیچ ابزاری نصب یا اجرا نشده است.

## اهداف

1. اجزای Ansible را بشناسید و بدانید **چرا Agentless بودن در شبکه یک مزیت بزرگ است**.
2. تفاوت State پایدارِ Resource در Terraform با روش معمول Ansible که State File مرکزیِ مشابه ندارد را با پیامد عملی بفهمید؛ Idempotency/Check در Ansible به Module و Workflow وابسته است.
3. `terraform plan` را پیش‌نمایش بدانید و توضیح دهید چرا **Apply یک Plan بازبینی‌نشده** می‌تواند خطرناک باشد.
4. قابلیت ابزارها را برای وظیفهٔ نمونه بسنجید و توضیح دهید چه زمانی ترکیب هر دو سودمند است و چگونه از دو منبع حقیقت جلوگیری می‌شود.
5. با ریسک واقعی اجرای Automation روی شبکه آشنا شوید.

## ۱. Ansible — پیکربندی بدون Agent

**Ansible** ابزار کنترل‌گرمحور است: Playbook و اتصال از ماشین کنترل اجرا می‌شوند و برای مدیریت شبکه معمولاً از SSH/CLI یا API بهره می‌برند؛ عموماً Agent دائمی روی Router/Switch نصب نمی‌شود.

**Agentless به معنی «هیچ پیش‌نیازی ندارد» نیست.** در اتصال `network_cli`، دستگاه و ماژول/Collection باید روش مدیریت را پشتیبانی کنند و اعتبارنامهٔ امن لازم است؛ بسیاری از ماژول‌های میزبان Linux به Python روی مقصد نیاز دارند. ماژول‌های شبکه از مسیر CLI/API استفاده می‌کنند و معمولاً به `gather_facts: false` همراه با ماژول Facts مخصوص شبکه نیاز دارند. انتخاب ابزار را براساس پشتیبانی دستگاه و نسخه انجام دهید، نه این فرض که همهٔ محصولات یا ماژول‌ها یکسان‌اند.

### اجزای اصلی

| جزء | چیست | مثال |
|---|---|---|
| **Inventory** | فهرست میزبان‌ها و گروه‌ها | `[switches]` با ۵ آی‌پی |
| **Playbook** | فایل YAML شامل Taskها | `create-vlan.yml` |
| **Task** | یک عمل مشخص | «VLAN 10 بساز» |
| **Module** | کد اجرایی یک عملیات | `cisco.ios.ios_vlans` |
| **Role** | بستهٔ قابل استفادهٔ مجدد | `common-vlans/` |
| **Variable** | مقدار پارامتر | `vlan_id: 10` |
| **Template** (Jinja2) | ساخت Config از متغیر | `vlan {{ id }}` |

### Inventory — نمونه

```ini
[switches]
sw1 ansible_host=10.10.0.11
sw2 ansible_host=10.10.0.12
sw3 ansible_host=10.10.0.13

[switches:vars]
ansible_network_os=cisco.ios.ios
ansible_connection=ansible.netcommon.network_cli
ansible_user=automation
```

- `[switches]` — یک **گروه**. Playbook می‌تواند روی گروه کار کند.
- `ansible_connection=ansible.netcommon.network_cli` — از افزونهٔ اتصال شبکه برای CLI/SSH استفاده می‌کند، نه ماژول عمومی Python روی Switch؛ نام کوتاه/نسخه می‌تواند فرق کند.
- `ansible_network_os=cisco.ios.ios` — خانوادهٔ ماژول‌ها را تعیین می‌کند.

### Playbook — نمونه

**طراحی‌شده، اجرا‌نشده:**

```yaml
---
- name: Ensure VLANs exist and are correct
  hosts: switches
  gather_facts: false
  tasks:
    - name: Create VLAN 10
      cisco.ios.ios_vlans:
        config:
          - vlan_id: 10
            name: USERS
        state: merged

    - name: Show resulting VLAN table
      cisco.ios.ios_command:
        commands:
          - show vlan brief
      register: vlan_output

    - name: Print result
      ansible.builtin.debug:
        var: vlan_output.stdout_lines
```

| بخش | معنا |
|---|---|
| `hosts: switches` | روی گروه Inventory اجرا شود |
| `gather_facts: false` | اجرای خودکار ماژول عمومی `setup` را متوقف می‌کند؛ برای تجهیزات `network_cli` از Fact-Gathering ماژول اختصاصیِ پشتیبانی‌شده استفاده کنید |
| `state: merged` | «این VLAN را اضافه کن، بقیه را دست نزن» |
| `register` | خروجی را در متغیر می‌گذارد |
| `debug` | نمایش برای بررسی |

**`state` — تفاوت حیاتی (برای `cisco.ios.ios_vlans`؛ مستند نسخهٔ نصب‌شده ملاک است):**

| state | رفتار |
|---|---|
| `merged` | اضافه/به‌روزرسانی می‌کند، بقیه را **دست نمی‌زند** |
| `replaced` | Configuration VLANهای صریحاً اعلام‌شده را جایگزین می‌کند؛ دامنهٔ Attributeها را مستندات Module تعیین می‌کند |
| `overridden` | پیکربندی کلی VLANها را به فهرست مطلوب همگرا می‌کند و ممکن است VLANهای ذکرنشده را حذف کند — پرریسک |
| `deleted` | VLANهای صریحاً مشخص‌شده را حذف می‌کند، اگر Module/Device اجازه دهد |
| `purged` | حذف گسترده/کامل Resourceهای آن نوع در Moduleهای پشتیبان؛ جزئیات و محدودیت را پیش از استفاده بخوانید |

**دام مهم:** در Collection/ماژولی که این Stateها را پشتیبانی می‌کند، `overridden` می‌تواند VLANهای مدیریت‌نشده را نیز حذف کند و `purged` می‌تواند حذف گسترده‌تری انجام دهد؛ دامنهٔ اثر را از مستند نسخهٔ دقیق ماژول بخوانید. `--check` فقط وقتی مفید است که ماژول Check Mode را پشتیبانی کند و تضمین نمی‌کند تمام اثرهای دستگاه را شبیه‌سازی کند؛ خروجی و Diff را بازبینی و ابتدا در محیط آزمایشی اعتبارسنجی کنید.

### Idempotency در Ansible

`cisco.ios.ios_vlans` در نسخه‌های پشتیبان، Stateهای Resource-Module را برای همگرایی/Idempotency ارائه می‌کند؛ اگر VLAN و Attributeهای مطلوب دقیقاً موجود باشند، تکرار `merged` باید بدون تغییر باشد. خروجی `changed: false` را فقط پس از اجرای ماژول/نسخهٔ معین ثبت کنید.

**اما:** Idempotency را خود Ansible برای هر Task تضمین نمی‌کند؛ رفتار به Module و Mode وابسته است. فرمان خام در `ios_config`، Script یا Module ناپشتیبان ممکن است هر بار تغییر اعلام کند یا اثر ناخواسته داشته باشد؛ اجرای تکراری را در Lab بررسی کنید.

## ۲. Terraform — Stateful و Declarative

**Terraform** منابع را با **HCL** تعریف می‌کند و State پایدار نگه می‌دارد تا منابع مدیریت‌شده و شناسه/ویژگی‌های شناخته‌شدهٔ آن‌ها را ردیابی کند. Providerها هنگام Plan می‌توانند وضعیت سرویس را Refresh کنند؛ State به‌تنهایی نمایش زنده و تضمین‌شدهٔ واقعیت نیست.

### سه مفهوم کلیدی

| مفهوم | چیست |
|---|---|
| **Configuration** (`.tf`) | وضعیت **مطلوب** |
| **State** (`.tfstate`) | آخرین State/شناسه‌هایی که Terraform برای Resourceهای مدیریت‌شده ثبت/می‌شناسد؛ لزوماً تصویر زنده نیست |
| **Plan** | پیش‌نمایش عملیات پیشنهادی پس از مقایسهٔ Configuration، State و—اگر Provider اجرا/پشتیبانی کند—وضعیت Refresh‌شدهٔ منابع |

```text
Configuration (مطلوب)  ─┐
                        ├─→  Plan  ─→  Apply
State (ثبت‌شده)         ─┘
```

### نمونهٔ HCL

**طراحی‌شده، اجرا‌نشده:**

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

resource "aws_vpc" "lab" {
  cidr_block = "10.10.0.0/16"

  tags = {
    Name = "lab-vpc"
  }
}
```

| بخش | معنا |
|---|---|
| `required_providers` | Provider و نسخه — **قفل نسخه حیاتی است** |
| `resource "aws_vpc" "lab"` | نوع منبع + نام محلی |
| `tags` | برچسب‌ها |

**قفل نسخه و بازبینی Plan:** اگر Provider یا ماژول تغییر کند، رفتار/تفسیر Resource ممکن است عوض شود؛ نسخه‌ها و Lock File را کنترل کنید. قید `~> 5.0` معمولاً نسخه‌های سازگارِ کمتر از 6.0 را می‌پذیرد؛ معنی Constraint را دقیق بخوانید.

`terraform plan` پیش‌نمایش تغییرات پیشنهادی است و به‌خودی‌خود `apply` نمی‌کند؛ معمولاً Providerها برای Refresh خواندن‌هایی از سرویس انجام می‌دهند. Plan می‌تواند Resource را `add`, `change`, `replace` یا `destroy` کند. **Apply کردن Plan بدون بازبینی** (به‌ویژه Replace/Destroy، وابستگی‌ها، State و مقصد) خطر دارد؛ Plan نیز نتیجهٔ نهایی سرویس را تضمین نمی‌کند.

### State — نقطهٔ قوت و ضعف

**قوت:** Terraform **می‌داند** چه چیزی ساخته و می‌تواند حذف/تغییر دهد.

**ضعف:** State می‌تواند **Desync** شود:

- کسی از طریق کنسول ابری منبعی را دستی حذف کند.
- State قدیمی باشد.
- دو نفر هم‌زمان Apply کنند (نیاز به Locking).

**نتیجه:** State ممکن است با منبع واقعی واگرا باشد. `terraform plan` معمولاً تلاش می‌کند با Provider وضعیت منابع را Refresh و تغییرهای خارج از Terraform را نشان دهد، اما این رفتار به منبع، مجوز و Provider وابسته است؛ Refresh غیرفعال یا ناقص، State قدیمی و منبعِ خارج از دید Provider می‌تواند اختلاف را پنهان کند. برای کار تیمی از Backend مشترکِ پشتیبانی‌شده با کنترل دسترسی و Locking استفاده کنید؛ قابلیت Locking به Backend وابسته است و نباید مفروض گرفته شود.

**هشدار امنیتی:** فایل `.tfstate` می‌تواند **گذرواژه و کلید** داشته باشد. این فایل نباید در Git باشد؛ باید در Backend رمزنگاری‌شده باشد.

## ۳. Ansible در برابر Terraform — مقایسهٔ دقیق

| محور | **Ansible** | **Terraform** |
|---|---|---|
| مدل معمول | Playbook، Inventory و Module برای Configuration/Orchestration | Configuration اعلانی، Resource Graph و چرخهٔ عمر از طریق Provider |
| زبان اصلی | YAML (Playbook) | HCL |
| اتصال/Agent | معمولاً بدون Agent دائمی روی Network Device؛ نیازمند مسیر و ماژول CLI/API پشتیبانی‌شده | Provider از API/SDK/روش مستند سرویس استفاده می‌کند؛ نوع اتصال به Provider بستگی دارد |
| وضعیت منابع | معمولاً State File مرکزیِ منبع‌به‌منبع مانند Terraform ندارد؛ ماژول می‌تواند وضعیت مطلوب را Idempotent اعمال کند | State پایدار برای ردیابی Resourceهای مدیریت‌شده نگه می‌دارد |
| تکرار/پیش‌نمایش | تکرار می‌تواند بدون تغییر باشد، اگر ماژول مناسب و Idempotent باشد؛ Check Mode وابسته به پشتیبانی است | Plan عملیات پیشنهادی را پس از مقایسه/Refresh نشان می‌دهد؛ Apply جداگانه انجام می‌شود |
| کاربرد رایج | پیکربندی تجهیزات/سیستم‌ها و Orchestration با CLI/API | چرخهٔ عمر Resourceهایی که Provider پشتیبانی می‌کند |
| تشخیص Drift | Check/Gather و نتیجه به ماژول، Collection و Workflow وابسته است | Refresh/Plan می‌تواند Drift را نشان دهد، اما به State و دید Provider محدود است |
| کاربرد در شبکه | Collectionهای Network CLI/API با توجه به Image و نسخه | Providerهای شبکه/ابر در صورت پشتیبانی؛ قابلیت Provider تعیین‌کننده است |
| مقیاس‌پذیری | موازی‌سازی و محدودیت‌ها با Inventory/Strategy و دستگاه‌ها تنظیم می‌شود | موازی‌سازی و محدودیت‌ها با Graph، Provider و API مقصد وابسته است؛ کارایی را باید اندازه گرفت |

### انتخاب ابزار و تعیین مالکیت تغییر

استفادهٔ هم‌زمان از دو ابزار ذاتاً نادرست نیست؛ در یک Pipeline ممکن است Terraform منابعی را ایجاد کند و Ansible پس از آن سیستم/تجهیز را پیکربندی کند. خطر زمانی بالا می‌رود که **یک Resource یا فیلد پیکربندی واحد** را هم‌زمان دو ابزار مدیریت کنند، یا ترتیب و تحویل State/خروجی‌ها مشخص نباشد.

| نیاز نمونه | گزینه‌ای که معمولاً بررسی می‌شود | شرط/محدودیت |
|---|---|---|
| ساخت VM، VPC یا Cloud Network | Terraform و Provider مربوط | API، مجوز، State و Lifecycle Provider را بررسی کنید |
| پیکربندی VLAN/ACL/Route روی Switch | Ansible و Network Collection سازگار | Image، نسخه، روش اتصال و Check/Idempotency ماژول مهم‌اند |
| ساخت Resource و سپس آماده‌سازی OS/شبکه | Terraform **و** Ansible در مراحل جدا | مالک هر Resource، خروجی‌های تحویلی و ترتیب اجرا را مستند کنید |

**قاعدهٔ مالکیت:** برای هر Resource/فیلد مشخص کنید کدام سامانه منبع حقیقت است؛ از دو ابزارِ ناسازگار که همان فیلد را می‌نویسند پرهیز کنید. Terraform نیز می‌تواند با Provider شبکه را پیکربندی کند و Ansible نیز در دامنه‌های دیگر Resource بسازد؛ تقسیم‌بندی بالا گرایش رایج است، نه مرز فنی مطلق.

## ۴. Pipeline و CI/CD

```text
Git (منبع حقیقت)
   │
   ├─→ Lint (yamllint / terraform validate)
   ├─→ پیش‌نمایش (Check Modeِ پشتیبانی‌شده / terraform plan)
   ├─→ بازبینی اثر و تأیید انسانی (برای تغییرات حساس)
   ├─→ Apply
   └─→ Verification (show commands، تست Connectivity)
```

| مرحله | هدف | چرا |
|---|---|---|
| **Git** | تاریخچه و بازبینی | هر تغییر قابل بازگشت |
| **Lint/Validate** | خطای نگارشی | جلوگیری از خطای ساده |
| **پیش‌نمایش** | Check Mode فقط برای Module پشتیبان؛ Plan برای Terraform | دیدن پیشنهاد تغییر پیش از Apply؛ شبیه‌سازی کامل همهٔ پیامدها را تضمین نمی‌کند |
| **تأیید انسانی** | کنترل تغییر | برای حذف/بازنویسی |
| **Verification** | اثبات نتیجه | Automation بدون Verification کافی نیست |

**نکتهٔ کلیدی:** Automation **بدون Verification** یک بمب ساعتی است. اگر Playbook «موفق» گزارش داد ولی VLAN ساخته نشد، بدون Check متوجه نمی‌شوید. Verification باید **بخشی از Pipeline** باشد، نه کار دستی بعد از آن.

## ۵. سناریوی طراحی‌شده

**تمرین مستقلِ طراحی‌شده و اجرا‌نشده:** بخش Ansible برای اجرای آینده به یک ماشین کنترل و یک Image سازگارِ مدیریت شبکه نیاز دارد؛ PNETLab فقط می‌تواند میزبان احتمالی Image باشد و این کاربرگ در آن آزمایش نشده است. بخش Terraform جدا و اختیاری است و Provider آزمایشی لازم دارد. **هیچ Playbook، Plan یا شبکه‌ای اجرا نشده است.**

```text
┌──────────────┐     SSH/CLI      ┌─────────┐
│  Ansible     │ ───────────────→ │  SW1    │
│  (کنترل)     │ ───────────────→ │  SW2    │
│              │ ───────────────→ │  SW3    │
└──────────────┘                  └─────────┘
      ↑
   Inventory + Playbook (Git)

┌──────────────┐    Provider API  ┌─────────────┐
│  Terraform   │ ───────────────→ │  منابع ابری │
│  (کنترل)     │                  │  / VM       │
└──────────────┘                  └─────────────┘
      ↑
   HCL + State (Backend)
```

![نمودار قابل ویرایش ابزارهای پیکربندی؛ اجرا‌نشده](academy-images/aut-08-config.svg)

**سناریوی خطر طراحی‌شده، نه اجراشده:** اگر Playbook با `state: overridden` فقط VLAN 10 را در فهرست مطلوب اعلام کند، ماژول سازگار ممکن است VLANهای مدیریت‌نشده را حذف کند. دامنهٔ واقعی حذف به Collection/نسخه وابسته است؛ قبل از Apply، مستندات و خروجی Check/Plan را در Lab بررسی کنید و Backup/روش بازگشت داشته باشید. هیچ VLAN واقعی پاک نشده است.

## ۶. کاربرگ مستقلِ تشخیص قابلیت‌ها (اختیاری، طراحی‌شده و اجرا‌نشده)

**پیش‌نیاز Ansible:** محیط کنترل مجزا، نسخهٔ Ansible و Collectionهای ثبت‌شده، دو Router/Switch آزمایشگاهی با IOS/IOS XE سازگار، دسترسی Console برای بازگشت و حساب آزمایش کم‌امتیاز. هیچ اتصال به شبکهٔ عملیاتی یا ابرِ دارای هزینه ایجاد نکنید. PNETLab ممکن است میزبان Image باشد، اما پشتیبانی CLI/API باید برای همان Image و نسخه تأیید شود. رمزها را در Inventory ساده، Git، Screenshot یا history قرار ندهید؛ از Vault/سازوکار Secret مناسب استفاده کنید.

1. روی ماشین کنترل، نسخهٔ Ansible و نسخه/وجود Collection (`cisco.ios`, `ansible.netcommon`) را ثبت کنید. `ansible.builtin.ping` برای میزبان Python‌دار است و **آزمون مناسب دسترسی IOS با `network_cli` نیست**.
2. Inventory دو Switch را با `ansible_connection=ansible.netcommon.network_cli` و `ansible_network_os=cisco.ios.ios` بسازید؛ ابتدا یک دستور صرفاً خواندنی نظیر `cisco.ios.ios_command` با `show version` اجرا و خروجی/نسخه را ثبت کنید. نحو دقیق را با مستند Collection نصب‌شده تطبیق دهید.
3. Playbook `ios_vlans` را با `state: merged` برای VLAN آزمایشی بنویسید. در Snapshot دورریختنی، فقط اگر ماژول پشتیبانی می‌کند، Check Mode را اجرا و نتیجه را بررسی کنید؛ سپس اجرای مجاز و دو اجرای تکراری را مقایسه کنید. `changed: false` را فقط پس از مشاهده ثبت کنید.
4. روی همان Lab و پس از Backup، Plan/Check مربوط به `overridden` را بررسی کنید. اگر ماژول Check Mode را پشتیبانی نمی‌کند یا اثرش مبهم است، آن را Apply نکنید و «قابل پیش‌نمایش/اجرا نبود» ثبت کنید.
5. Terraform را فقط با Provider محلی/آزمایشیِ شناخته‌شده و بدون ایجاد منبع پولی آماده کنید؛ `init` و `plan` را صرفاً اگر Dependency و دسترسی موجود است اجرا کنید. **Plan را Apply نکنید** مگر روی محیط disposable با تأیید و برنامهٔ بازگشت.
6. State را فقط در نمونهٔ آزمایشی و با حذف/پوشاندن مقادیر حساس بررسی کنید؛ فایل State واقعی را در Git یا گزارش منتشر نکنید.
7. تمرین Drift را فقط با Resource disposable و Providerی که Refresh را پشتیبانی می‌کند انجام دهید؛ در غیر این صورت این محدودیت را ثبت کنید.
8. شاهد Verification را از اجرای مجاز `show vlan brief` و خروجی/ساختار قابل‌بررسی ثبت کنید؛ پیام موفق Playbook به‌تنهایی اثبات حالت نهایی نیست.

**هشدار وضعیت:** این‌ها دستورالعمل طراحی‌شده‌اند، نه گزارش اجرا. اگر Image، Collection، Provider یا مجوز فراهم نیست، «اجرا‌نشده/پشتیبانی‌نشده» بنویسید؛ خروجی نمونه را شاهد واقعی ننامید.

## ۷. سؤال‌ها و پاسخ

1. **Ansible در مدیریت شبکه معمولاً Agentless است؟** بله؛ معمولاً روی Router/Switch Agent دائمی نصب نمی‌کند و از CLI/API می‌رود. این به معنی نبود پیش‌نیاز در ماشین کنترل، Collection یا دستگاه نیست.

2. **چرا این مدل برای شبکه مفید است؟** بسیاری از تجهیزات، محیط اجرای Agent عمومی ندارند؛ مدیریت از CLI/API سازگار امکان اتوماسیون را فراهم می‌کند. قابلیت هر Image/مدل باید بررسی شود.

3. **Inventory چیست؟** فهرست میزبان‌ها و گروه‌ها، همراه با متغیرهای اتصال.

4. **Playbook چیست؟** فایل YAML شامل Taskها.

5. **Module چیست؟** کد اجرایی یک عملیات مشخص (مثلاً `ios_vlans`).

6. **Role چیست؟** بستهٔ قابل استفادهٔ مجدد از Task/متغیر/Template.

7. **چرا در Play شبکه معمولاً `gather_facts: false` می‌گذاریم؟** تا Ansible ماژول عمومی `setup` را مثل یک Linux Host اجرا نکند؛ در صورت نیاز از ماژول Facts اختصاصی و سازگار استفاده می‌شود.

8. **تفاوت `merged` و `overridden` چیست؟** برای Module/Collectionی که این Stateها را پشتیبانی می‌کند، `merged` تغییرهای درخواستی را با وضعیت موجود ادغام می‌کند؛ `overridden` می‌تواند منابع/تنظیمات خارج از فهرست مطلوب را حذف یا جایگزین کند. تعریف و دامنه را در نسخهٔ ماژول بخوانید.

9. **Terraform چه زبانی دارد؟** HCL.

10. **State در Terraform چیست؟** نگاشت Resourceهای مدیریت‌شده به شناسه/ویژگی‌هایی است که Terraform می‌شناسد؛ ممکن است از منبع زنده واگرا شود.

11. **Plan چیست؟** پیش‌نمایش تغییرهای پیشنهادی پس از مقایسهٔ Configuration، State و Refreshی که Provider پشتیبانی می‌کند؛ Apply نیست.

12. **Terraform برای چه مناسب است؟** چرخهٔ عمر Resourceهایی که Provider آن‌ها را پشتیبانی می‌کند؛ Providerهای شبکه نیز وجود دارند، اما پوشششان متفاوت است.

13. **Ansible برای چه مناسب است؟** Playbookهای Configuration/Orchestration روی سیستم‌ها و تجهیزات از طریق CLI/API، به شرط سازگاری Module و مقصد.

14. **Drift چیست؟** تفاوت بین وضعیت واقعی و وضعیت تعریف‌شده.

15. **چرا `.tfstate` نباید در Git باشد؟** ممکن است گذرواژه و کلید داشته باشد.

16. **CI/CD چه نقشی دارد؟** خودکارسازی Lint، Dry Run، تأیید و Verification.

17. **Automation بدون Verification چه مشکلی دارد؟** «موفق» گزارش می‌شود حتی اگر نتیجه اعمال نشده باشد.

18. **آیا در این درس ابزاری اجرا شده است؟** خیر.

## واژه‌نامه و چک‌لیست

**Ansible**: مدیریت پیکربندی معمولاً Agentless؛ **Terraform**: IaC با State ثبت‌شده؛ **Inventory**: فهرست میزبان؛ **Playbook**: فایل Task؛ **Module**: واحد عملیاتی؛ **Role**: بستهٔ قابل استفادهٔ مجدد؛ **State**: شناسه/ویژگی‌های ثبت‌شدهٔ Resourceها، نه الزاماً وضعیت زنده؛ **Plan**: پیش‌نمایش تغییر؛ **HCL**: زبان Terraform؛ **Drift**: واگرایی وضعیت؛ **Idempotent**: تکرار بی‌اثر.

- [ ] Ansible و Terraform را در دامنهٔ درست به‌کار می‌برم.
- [ ] State و Plan را می‌شناسم و `.tfstate` را در Git نمی‌گذارم.
- [ ] `state` ماژول Ansible را قبل از اجرا بررسی می‌کنم.
- [ ] Dry Run را قبل از اعمال اجرا می‌کنم.
- [ ] Verification را بخشی از Pipeline می‌کنم.
- [ ] از «دو منبع حقیقت» پرهیز می‌کنم.
- [ ] هیچ ابزاری را اجراشده اعلام نمی‌کنم.
