# درس ۰.۲ — CPU، حافظه، ذخیره‌سازی و کارت شبکه

> **وضعیت:** پیش‌نویس برای بازبینی محتوایی؛ هنوز تأیید و به کاتالوگ اضافه نشده است. سناریوها، اعداد، تمرین و خروجی‌ها آموزشی و فرضی‌اند؛ هیچ ابزار، VM یا سخت‌افزاری برای این درس اجرا و اعتبارسنجی نشده است.

## ۱. محدوده و اهداف

**پیش‌نیاز:** درس ۰.۱؛ آشنایی با سخت‌افزار، سیستم‌عامل، برنامه، فرایند و مسیر سادهٔ یک درخواست.

این درس یک مبنای عمومی IT است، نه ادعای پوشش یک هدف مستقل Cisco. هدف تعمیر دستگاه یا آموزش عمیق معماری پردازنده نیست. جزئیات مجازی‌سازی و شبکه در درس‌های بعدی بررسی می‌شوند.

در پایان باید بتوانید:

1. CPU، Core، Thread و Cache را با یکدیگر مقایسه کنید.
2. تفاوت ظرفیت RAM با Storage و اثر محدودیت منابع را توضیح دهید.
3. HDD، SSD و مفهوم RAID را در حد تصمیم‌گیری مقدماتی مقایسه کنید.
4. نقش NIC، سرعت لینک و نیاز به بررسی خطاهای ارتباطی را توضیح دهید.
5. از روی چند شاهد فرضی، فرضیه‌های منابع یا ارتباط را مطرح کنید، نه تشخیص قطعی بدون داده.

## ۲. تصویر کلی: یک درخواست و چند منبع

فرض کنید کاربر صفحهٔ یک سرویس داخلی را باز می‌کند. درخواست از شبکه به NIC میزبان می‌رسد؛ سیستم‌عامل آن را به سرویس تحویل می‌دهد. CPU دستورهای سرویس را اجرا می‌کند؛ داده‌های فعال در RAM نگهداری می‌شوند. ممکن است سرویس به فایل یا داده‌ای در Storage یا به سرویس دیگری نیاز داشته باشد. پاسخ دوباره از مسیر شبکه به کاربر می‌رسد.

```text
[کاربر] ← شبکه → [NIC میزبان] ← سیستم‌عامل → [سرویس]
                                             │
                                          CPU ↔ Cache
                                             │
                                            RAM
                                             │ در صورت نیاز
                                     Storage / سرویس دیگر
```

این تصویر روابط را ساده کرده است؛ نمایش دقیق مسیر گذرگاه‌ها یا همهٔ لایه‌های نرم‌افزار نیست. هر درخواست الزاماً خواندن فیزیکی از دیسک انجام نمی‌دهد: داده ممکن است از قبل در حافظه باشد یا از سرویس دیگری بیاید.

**تشبیه:** CPU مانند کارکنانی است که دستورها را اجرا می‌کنند، RAM شبیه میز کار نزدیک آن‌ها و Storage شبیه قفسهٔ نگهداری است. این تشبیه برای آغاز است؛ رفتار واقعی پردازنده، Cache و سیستم‌عامل پیچیده‌تر از یک دفتر است.

## ۳. CPU، Core و Thread

### CPU و Core

**CPU** دستورهای برنامه را اجرا می‌کند. یک CPU می‌تواند چند **Core** یا هسته داشته باشد؛ هر هسته منابع پردازشی برای اجرای دستورها دارد. چند هسته می‌توانند در شرایط مناسب چند بخش مستقل کار را هم‌زمان پیش ببرند.

داشتن دو برابر هسته به‌تنهایی به معنی دو برابر شدن سرعت هر برنامه نیست. توان بهره‌گیری برنامه از هم‌زمانی، محدودیت حافظه، Storage، شبکه و عوامل دیگر بر نتیجه اثر دارند.

### Thread را در دو معنا بشناسیم

- **Thread نرم‌افزاری:** یک مسیر اجرای دستور درون فرایند که سیستم‌عامل آن را زمان‌بندی می‌کند.
- **Thread سخت‌افزاری یا Logical CPU:** یک جایگاه اجرای قابل مشاهده برای زمان‌بند که ممکن است با فناوری‌هایی مانند SMT از یک هسته ارائه شود.

این دو اصطلاح به هم مربوط‌اند، اما یک چیز نیستند. برای مثال، در دستگاهی فرضی با ۴ هسته و ۲ Thread سخت‌افزاری برای هر هسته، سیستم‌عامل ممکن است ۸ Logical CPU ببیند. این به معنی وجود ۸ هستهٔ فیزیکی یا دو برابر شدن قطعی توان پردازش نیست؛ منابعی در یک هسته مشترک‌اند و بهره به نوع کار بستگی دارد.

### زمان‌بندی و رقابت منابع

سیستم‌عامل Threadهای آمادهٔ اجرا را زمان‌بندی می‌کند. اگر درخواست‌ها افزایش یابند، ممکن است کارها منتظر منابع بمانند. بااین‌حال، **کندی به‌تنهایی اثبات کمبود CPU نیست**: سرویس ممکن است منتظر ذخیره‌سازی، شبکه یا وابستگی دیگری باشد.

## ۴. Cache و RAM

### Cache چیست؟

Cache حافظه‌ای کوچک‌تر و معمولاً سریع‌تر نزدیک پردازنده است که نسخه‌ای از داده‌های پرکاربرد را نگه می‌دارد تا دسترسی به آن‌ها سریع‌تر شود. معمولاً سطوحی مانند L1، L2 و L3 وجود دارند؛ اندازه، اشتراک و عملکرد آن‌ها به معماری بستگی دارد.

Cache با **RAM** و همچنین Cache نرم‌افزاری فایل یکی نیست، اگرچه همه از ایدهٔ نگهداری موقت اطلاعات استفاده می‌کنند.

### RAM چیست؟

RAM فضای کاری فرایندهای در حال اجرا و سیستم‌عامل است. محتوای RAM معمولاً با قطع برق از دست می‌رود. ظرفیت ناکافی می‌تواند باعث فشار حافظه و استفاده از فضای کمکی روی Storage شود؛ این ممکن است عملکرد را کاهش دهد. رفتار دقیق و نام این فضا به سیستم‌عامل و تنظیمات بستگی دارد.

**نکته:** عدد «RAM استفاده‌شده» به‌تنهایی خرابی را اثبات نمی‌کند؛ سیستم‌عامل ممکن است از حافظه برای Cache هم استفاده کند. حافظهٔ قابل استفاده، فشار حافظه، رفتار برنامه و شواهد مرتبط باید با هم بررسی شوند.

## ۵. Storage: HDD، SSD و RAID

### HDD و SSD

| ویژگی | HDD | SSD |
|---|---|---|
| فناوری عمومی | دیسک چرخان و اجزای مکانیکی | حافظهٔ الکترونیکی بدون بخش چرخان برای ذخیره‌سازی |
| تأخیر دسترسی | معمولاً بیشتر، به‌ویژه برای دسترسی تصادفی | معمولاً کمتر؛ بسته به نوع و رابط |
| نکتهٔ انتخاب | ظرفیت و هزینه، حساسیت مکانیکی | نوع رابط، ظرفیت، دوام و بارکاری |

مقایسهٔ واقعی به مدل و بارکاری بستگی دارد. SSD به معنی «خراب‌نشدن» یا بی‌نیازی از Backup نیست. مفاهیم ظرفیت، تأخیر، نرخ انتقال و تعداد عملیات، ویژگی‌های متفاوت‌اند؛ سرعت بالای اعلام‌شده یک معیار واحد برای همهٔ کاربردها نیست.

### RAID در حد مقدماتی

RAID چند دیسک را طبق یک روش برای اهدافی مانند دسترس‌پذیری یا کارایی سازمان می‌دهد. رفتار دقیق وابسته به پیاده‌سازی، کنترلر و وضعیت آرایه است.

| نمونه | ایدهٔ مقدماتی | محدودیت مهم |
|---|---|---|
| RAID 0 | توزیع داده بین دیسک‌ها برای کارایی | افزونگی ندارد؛ خرابی یک عضو می‌تواند کل دادهٔ آرایه را از دسترس خارج کند |
| RAID 1 | نگهداری نسخه‌های آینه‌ای | خرابی برخی اعضا قابل تحمل است، اما ظرفیت قابل استفاده با مجموع خام برابر نیست |
| RAID 5 | توزیع داده و اطلاعات افزونگی؛ حداقل سه دیسک | معمولاً خرابی یک عضو را تحمل می‌کند؛ بازسازی و خرابی‌های بعدی ریسک دارند |

**RAID جایگزین Backup نیست.** حذف اشتباه، خرابی منطقی، باج‌افزار یا از دست رفتن میزبان می‌توانند دادهٔ موجود در آرایه را تحت تأثیر قرار دهند. Backup مستقل و آزمون بازیابی باید جداگانه طراحی شوند؛ جزئیات در درس ۰.۹ می‌آیند. هیچ آرایه‌ای در این درس ساخته یا آزمایش نمی‌شود.

## ۶. NIC و ارتباط شبکه

**NIC** یا کارت/رابط شبکه، میزبان را از طریق رسانهٔ مناسب به شبکه متصل می‌کند. این رابط می‌تواند فیزیکی یا در محیط مجازی به‌صورت مجازی ارائه شود؛ معماری VM در درس ۰.۷ می‌آید.

برای یک رابط اترنت، موارد زیر به تفکیک بررسی می‌شوند:

- **وضعیت لینک:** آیا ارتباط فیزیکی یا منطقی برقرار گزارش می‌شود؟
- **سرعت توافق‌شده:** برای نمونه، ۱ Gbps ظرفیت اسمی لینک است؛ تضمین سرعت کاربردی یا سرعت انتهابه‌انتها نیست.
- **Duplex:** ارتباط دوطرفهٔ هم‌زمان یا غیرهم‌زمان بسته به فناوری و تنظیمات؛ تفاوت و Auto-Negotiation در درس Ethernet عمیق‌تر بررسی می‌شوند.
- **خطا و شمارنده‌ها:** افزایش برخی خطاها می‌تواند سرنخ باشد، اما نوع خطا، نرخ تغییر، کابل، طرف مقابل و وضعیت کلی باید بررسی شوند.

سبز بودن چراغ رابط یا گزارش up نشان‌دهندهٔ موفقیت DNS، سرویس وب، مجوز کاربر یا کل مسیر نیست. کندی شبکه هم بدون بررسی می‌تواند با کندی سرویس اشتباه گرفته شود.

## ۷. سناریوی سازمانی: گزارش «سامانه کند است»

### وضعیت فرضی

یک سامانهٔ داخلی پس از افزایش تعداد کاربران کند شده است. داده‌های زیر **فرضی‌اند** و از دستگاه واقعی جمع‌آوری نشده‌اند:

| مشاهده | مقدار فرضی | برداشت اولیه، نه تشخیص |
|---|---|---|
| بار CPU | در دورهٔ مشکل، نزدیک ظرفیت برای چند دقیقه | فشار CPU یک فرضیه است؛ فرایندهای مسئول و انتظار سایر منابع بررسی شوند |
| RAM | فشار حافظه افزایش یافته است | احتمال رقابت بر سر حافظه بررسی شود؛ یک عدد مصرف به‌تنهایی کافی نیست |
| Storage | تأخیر خواندن نسبت به خط پایه افزایش یافته است | احتمال انتظار برای I/O وجود دارد؛ هم‌زمانی و علت هنوز مشخص نیست |
| رابط شبکه | لینک برقرار است؛ شمارندهٔ خطا در حال افزایش است | کیفیت ارتباط نیازمند بررسی است؛ لینک up به‌تنهایی سلامت مسیر را ثابت نمی‌کند |

این نشانه‌ها هم‌زمان می‌توانند چند مشکل یا یک زنجیرهٔ علت و معلول را نشان دهند. ترتیب وقوع، نوع بار و مقایسه با خط پایه را ثبت کنید. افزایش هسته، RAM یا تعویض کابل قبل از شناخت علت، راه‌حل اثبات‌شده نیست.

### پرسش‌های راهنما

1. مشکل برای همهٔ کاربران است یا فقط یک بخش؟ از چه زمانی شروع شده؟
2. کدام سرویس یا فرایند در دورهٔ کندی منابع بیشتری می‌خواهد؟
3. فشار حافظه و تأخیر Storage چه زمانی نسبت به بار CPU تغییر کرده‌اند؟
4. کدام شمارندهٔ رابط افزایش یافته و طرف مقابل چه وضعیتی دارد؟
5. پیش از تغییر، چه اثر و برنامهٔ بازگشتی باید بررسی شود؟

## ۸. کاربرگ مستقل: تحلیل و انتخاب فرضیه

**وضعیت:** کاربرگ کاغذی، طراحی‌شده و اجرا‌نشده؛ بدون نیاز به PNETLab یا دسترسی به میزبان واقعی.

### مراحل دانشجو

1. نمودار بخش ۲ را بازنویسی کنید و نقش CPU، RAM، Storage و NIC را مشخص کنید.
2. برای هر ردیف جدول سناریو یک فرضیه و یک شاهد تکمیلی لازم بنویسید.
3. دو فرضیهٔ متفاوت برای کندی مطرح کنید که یکی به منابع میزبان و دیگری به ارتباط مربوط باشد.
4. توضیح دهید چرا «لینک up» و «سرویس در حال اجرا» به‌تنهایی پاسخ‌گویی مناسب را ثابت نمی‌کنند.
5. یک اقدام مشاهده‌ای کم‌خطر و یک تغییر احتمالی نیازمند مجوز را مشخص کنید.

### پاسخ راهنما

- CPU: بررسی روند بار و فرایندهای مرتبط؛ فرضیهٔ فشار پردازش هنوز باید با بارکاری و زمان وقوع تطبیق یابد.
- RAM: بررسی فشار حافظه و رفتار برنامه، نه فقط درصد مصرف.
- Storage: مقایسهٔ تأخیر و خطا با خط پایه و زمان گزارش‌شده.
- NIC: بررسی نوع و نرخ افزایش خطا و وضعیت طرف مقابل؛ افزایش یک شمارنده به‌تنهایی علت قطعی نیست.
- تغییر احتمالی: افزودن منابع یا تعویض قطعه نیازمند شواهد، تأیید، برنامهٔ اجرا و بازگشت است.

## ۹. Verification و Troubleshooting

هیچ فرمان یا خروجی سیستم واقعی در این درس ادعا نمی‌شود. در یک محیط واقعی، ابزار و معنای شاخص‌ها به سیستم‌عامل، نسخه و مجوز دسترسی بستگی دارند.

| مورد | بررسی پیشنهادی | تفسیر محتاطانه |
|---|---|---|
| CPU | روند زمانی، فرایندهای پرمصرف و نوع بار | مصرف بالا لزوماً خطا نیست؛ با کندی و ظرفیت مورد انتظار مقایسه شود |
| RAM | حافظهٔ در دسترس، فشار حافظه و رفتار فرایندها | مصرف Cache با کمبود واقعی یکسان نیست |
| Storage | ظرفیت، تأخیر، خطاها و وضعیت پشتیبان | پر بودن یا تأخیر باید با اثر واقعی بر سرویس سنجیده شود |
| NIC | وضعیت، سرعت توافق‌شده، نوع و نرخ تغییر شمارنده‌ها | up بودن، سلامت کل مسیر را ثابت نمی‌کند |
| سرویس | آزمون مجاز درخواست و لاگ‌ها | اجرا بودن فرایند معادل پاسخ صحیح به کاربر نیست |

ابتدا دامنه و زمان مشکل را ثبت کنید، سپس فرضیه بسازید، شواهد را مقایسه کنید و تنها با مجوز تغییر دهید. داده را برای آزادسازی فضا بدون شناخت و مجوز حذف نکنید.

## ۱۰. آزمون سناریویی با پاسخ تشریحی

### ۱) یک CPU دارای ۴ Core و دو Thread سخت‌افزاری در هر Core است. آیا الزاماً ۸ Core دارد؟
**پاسخ:** خیر. سیستم‌عامل ممکن است ۸ Logical CPU ببیند، اما Core فیزیکی چهار عدد است و منابع در هر هسته می‌توانند مشترک باشند.

### ۲) برنامه تک‌ریسمانی کند است. آیا دو برابر کردن Core حتماً سرعت آن را دو برابر می‌کند؟
**پاسخ:** خیر. توان استفادهٔ برنامه از موازی‌سازی و محدودیت سایر منابع اهمیت دارند.

### ۳) تفاوت Thread نرم‌افزاری و سخت‌افزاری چیست؟
**پاسخ:** اولی مسیر اجرای دستور در برنامه است؛ دومی جایگاه اجرای قابل مشاهده برای زمان‌بند است. این دو یک مفهوم نیستند.

### ۴) مقدار RAM استفاده‌شده زیاد است. آیا فوراً RAM خراب است؟
**پاسخ:** خیر. Cache و بار عادی نیز حافظه مصرف می‌کنند؛ فشار حافظه، ظرفیت در دسترس و عملکرد سرویس را بررسی کنید.

### ۵) چرا Cache پردازنده را با Storage یکسان نمی‌دانیم؟
**پاسخ:** Cache معمولاً کوچک‌تر و نزدیک پردازنده برای دسترسی سریع‌تر به داده‌های پرکاربرد است؛ Storage برای نگهداری پایدارتر فایل و داده است.

### ۶) چرا وجود SSD نیاز به Backup را حذف نمی‌کند؟
**پاسخ:** SSD نیز می‌تواند خراب شود و حذف اشتباه یا خرابی منطقی را جلوگیری نمی‌کند؛ Backup مستقل و بازیابی جداگانه لازم است.

### ۷) RAID 0 در برابر خرابی یک عضو چه افزونگی‌ای می‌دهد؟
**پاسخ:** افزونگی نمی‌دهد؛ خرابی یک عضو می‌تواند دادهٔ کل آرایه را از دسترس خارج کند.

### ۸) چرا RAID 1 جای Backup نیست؟
**پاسخ:** خطای منطقی یا حذف اشتباه ممکن است بر نسخه‌های آینه‌ای نیز اثر بگذارد؛ نسخهٔ پشتیبان مستقل لازم است.

### ۹) لینک NIC با سرعت ۱ Gbps برقرار است. آیا سرعت دانلود کاربر حتماً ۱ Gbps است؟
**پاسخ:** خیر. این ظرفیت اسمی همان لینک است؛ محدودیت مسیر، سرویس، سربار و سایر عوامل سرعت کاربردی را تغییر می‌دهند.

### ۱۰) در دورهٔ کندی، CPU و تأخیر Storage هر دو افزایش یافته‌اند. کدام علت قطعی است؟
**پاسخ:** از این دو مشاهده علت قطعی معلوم نیست؛ ترتیب زمانی، بار، فرایندها و دادهٔ تکمیلی لازم است.

### ۱۱) شمارندهٔ خطای رابط در حال افزایش است. چه می‌کنید؟
**پاسخ:** نوع و نرخ خطا، وضعیت رسانه و طرف مقابل را با روش مجاز بررسی می‌کنیم؛ فوراً بدون شاهد قطعه را تعویض نمی‌کنیم.

### ۱۲) سرویس «در حال اجرا» است ولی پاسخ کند است. آیا مشکل منتفی است؟
**پاسخ:** خیر. وضعیت اجرا پاسخ صحیح و سریع را تضمین نمی‌کند؛ منابع، وابستگی‌ها، شبکه و لاگ‌ها بررسی می‌شوند.

## ۱۱. واژه‌نامه

| اصطلاح | معنی |
|---|---|
| CPU / Core | پردازنده / واحد پردازشی درون آن |
| Thread نرم‌افزاری | مسیر اجرای دستور در یک فرایند |
| Logical CPU | جایگاه اجرای قابل مشاهده برای زمان‌بند سیستم‌عامل |
| Cache | نگهداری موقت داده برای دسترسی سریع‌تر |
| RAM | حافظهٔ کاری معمولاً فرّار |
| Storage | محل نگهداری پایدارتر فایل و داده |
| HDD / SSD | ذخیره‌سازی مکانیکی چرخان / الکترونیکی |
| RAID | سازمان‌دهی چند دیسک با هدف و محدودیت مشخص |
| NIC | رابط اتصال میزبان به شبکه |
| Baseline | وضعیت مرجع برای مقایسهٔ رفتار آینده |

## ۱۲. جمع‌بندی و چک‌لیست

یک سرویس برای پاسخ‌گویی به منابع مختلف وابسته است؛ نشانهٔ کندی به‌تنهایی منبع مشکل را مشخص نمی‌کند. RAID و SSD جای Backup مستقل نیستند؛ وضعیت up رابط نیز سلامت کل ارتباط را ثابت نمی‌کند.

- [ ] Core، Thread نرم‌افزاری و Logical CPU را تفکیک می‌کنم.
- [ ] نقش Cache، RAM و Storage را با مثال توضیح می‌دهم.
- [ ] RAID 0، 1 و 5 را در حد مقدماتی و با محدودیت‌هایشان مقایسه می‌کنم.
- [ ] تفاوت سرعت اسمی لینک و عملکرد انتهابه‌انتها را می‌دانم.
- [ ] برای کندی، فرضیه و شاهد لازم می‌نویسم و بدون مجوز تغییر ایجاد نمی‌کنم.

**وضعیت:** پیش‌نویس برای بازبینی؛ سناریو و کاربرگ فرضی و اجرا‌نشده‌اند. تأیید محتوایی و عملی هنوز انجام نشده است.
