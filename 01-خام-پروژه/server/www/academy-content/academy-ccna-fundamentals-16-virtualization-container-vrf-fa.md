# CCNA NF-16 — مجازی‌سازی سرور، Container و VRF

**سطح:** CCNA مقدماتی. **پیش‌نیاز:** درس‌های مرحلهٔ صفر ۰.۶ و ۰.۷. **هدف رسمی مرتبط:** `1.12` با فعل Explain. **بازبینی ردیفی ۲۰۲۶-۱۱-۲۰:** نقش VM، Container و VRF در سطح متن کافی ارزیابی شد؛ هیچ VM/Container/VRF راه‌اندازی یا پلتفرم آزموده نشده است. **وضعیت:** پیش‌نویس؛ سناریوها و کاربرگ تحلیلی اجرا نشده‌اند.

## هدف‌ها

تفاوت مجازی‌سازی سرور، Container و VRF را در سطح مفهومی توضیح دهید؛ نقش Host، Guest، Kernel و جدول‌های مسیر جداگانه را از هم تفکیک کنید؛ محدودیت امنیتی و عملی هر مثال را بشناسید.

## ۱. مجازی‌سازی سرور

Hypervisor منابع Host را برای ساخت VMها مدیریت می‌کند. هر VM دستگاه‌های مجازی مانند vCPU، RAM، NIC و دیسک می‌بیند و می‌تواند Guest OS خود را اجرا کند. چند VM روی یک Host از منابع فیزیکی مشترک بهره می‌برند؛ سهم CPU/Memory، پهنای‌باند Storage، ظرفیت و مرز جداسازی به تنظیمات و Hypervisor بستگی دارد.

- **Type 1 (bare-metal):** Hypervisor مستقیماً روی سرور فیزیکی اجرا می‌شود.
- **Type 2 (hosted):** Hypervisor به‌صورت برنامه روی Host OS اجرا می‌شود.

هر دو نوع VM می‌سازند؛ «Type 1» یا داشتن VM به‌تنهایی امنیت، پشتیبان‌گیری، High Availability یا اتصال شبکه را تضمین نمی‌کند. vNIC مهمان ممکن است به یک Virtual Switch/Port Group وصل شود و بعد از آن، VLAN، Gateway، ACL و مسیر فیزیکی/مجازی هنوز باید درست باشند.

## ۲. Container

Container محیطی بسته‌بندی‌شده برای اجرای برنامه و وابستگی‌های آن با مرزهای OS-level است. Runtime با امکاناتی مانند namespace و کنترل منابع، Processها و منابع را جدا می‌کند. در مدل معمول Containerهای سیستم‌عاملی، آن‌ها از Kernel میزبان استفاده می‌کنند؛ این تفاوت مهمی با VM دارای Guest OS/Kernel مجزا است. Containerها معمولاً شروع و بسته‌بندی سبک‌تری دارند، اما هزینه و مرز امنیتی به runtime، image، مجوزها، host و پیکربندی بستگی دارد. Container به‌تنهایی تضمین امنیت یا جداسازی کامل نیست؛ VMها نیز اگر ضعیف تنظیم شوند امن نیستند.

| جنبه | VM معمول | Container سیستم‌عاملی معمول | VRF |
|---|---|---|---|
| چه چیزی جدا می‌شود؟ | سخت‌افزار مجازی/Guest OS | Process و فضای کار با قابلیت OS | Routing context و جدول‌های مسیر |
| هستهٔ سیستم‌عامل | Guest Kernel جداگانه | معمولاً Kernel میزبان | همان NOS/Router OS؛ VRF Kernel جدا نمی‌سازد |
| هدف اصلی | اجرای OS/Workload جدا | بسته‌بندی و اجرای برنامه/وابستگی | تفکیک مسیرها و فضای شبکهٔ منطقی |
| چه چیزی را خودکار نمی‌دهد؟ | پچ، Backup، دسترسی شبکه یا امنیت VM | جداسازی سخت‌افزاری کامل/اعتماد به Image | رمزنگاری، ACL کامل، Route Leak یا دسترسی بین VRFها |

تشبیه: VMها مانند واحدهایی با تاسیسات مستقل‌تر و Containerها مانند فضاهایی با بخشی از تاسیسات مشترک‌اند. این تشبیه درجهٔ امنیت واقعی را تعیین نمی‌کند.

## ۳. VRF

**VRF — Virtual Routing and Forwarding** سازوکاری برای نگهداری جدول‌های Routing مجزا در یک دستگاه پشتیبان است. به‌صورت مفهومی، یک Router می‌تواند مسیرهای مشتری A و B را جدا مدیریت کند؛ حتی فضای آدرس هم‌پوشان ممکن است در VRFهای مجزا قابل استفاده باشد. ارتباط بین VRFها خودکار فرض نمی‌شود و به طراحی Route Leaking یا سرویس‌های مربوط وابسته است.

به هر VRF می‌توان Interfaceهای مشخص را نسبت داد؛ دستگاه برای همان Routing Context، مسیرهای Connected/Static/Dynamic و Forwarding متناظر را نگه می‌دارد (اصطلاحات/پیاده‌سازی RIB و FIB به پلتفرم وابسته‌اند). جدول Global و VRFها را از هم جدا کنید: وجود Route در یک VRF، رسیدن از VRF دیگر را ثابت نمی‌کند. **Route leaking** انتقال گزینشی مسیر میان Contextهاست و به Policy، Firewall/ACL و کنترل تقارن مسیر نیاز دارد.

**مثال:** Tenant-A و Tenant-B هر دو از `10.0.0.0/24` استفاده می‌کنند. اگر Interface هر کدام به VRF مجزای خود تعلق داشته باشد، مقصد `10.0.0.10` در جدول A و جدول B می‌تواند به دو مسیر/میزبان متفاوت اشاره کند. این تکرار تنها در Contextهای مجزا معنی‌دار است؛ افزودن اشتباه هر دو Interface به Global routing table می‌تواند هم‌پوشانی بسازد. ارتباط دو Tenant به‌طور پیش‌فرض مجاز نیست و برای آن باید طرح انتقال، هویت مقصد و Policy مشخص شود.

VRF یک VM یا Container نیست و به‌تنهایی همهٔ نیازهای امنیتی یا رمزنگاری را برآورده نمی‌کند. Interface، پروتکل، syntax و فرمان‌های پشتیبانی‌شده به مدل و نسخه بستگی دارند.

```text
[Router سازگار]
 ├── VRF-A: جدول مسیر مستقل A ── شبکهٔ A
 └── VRF-B: جدول مسیر مستقل B ── شبکهٔ B
```

این نمودار مفهومی است، نه پیکربندی یا نتیجهٔ واقعی.

## ۴. سناریو و کاربرگ مستقل

**طراحی‌شده و اجرا‌نشده:** سازمانی می‌خواهد دو سرویس آزمایشی و دو محیط شبکه را جدا نگه دارد. تیم، VM یا Container را برای اجرای سرویس و VRF را برای جداسازی Routing بررسی می‌کند.

1. تعیین کنید کدام مفهوم به اجرای برنامه و کدام به جدول Routing مربوط است.
2. توضیح دهید چه اجزایی ممکن است مشترک بمانند و چه خطرات مشترکی بررسی می‌شوند.
3. اگر هر دو شبکه از یک محدودهٔ آدرس یکسان استفاده کنند، توضیح دهید چرا جدول‌های مسیر مجزا ممکن است کمک کنند و چرا ارتباط بین آن‌ها نیازمند طراحی است.
4. برای آزمایش واقعی، محصول، نسخه، ایمیج و مجوز و روش ثبت نتیجه را به‌عنوان پیش‌نیاز بنویسید؛ هیچ نصب یا دستور در این درس اجرا نشود.

**پاسخ راهنما:** VM/Container محیط اجرای سرویس‌اند، VRF تفکیک جدول مسیر است. جداسازی Routing جای کنترل دسترسی و رمزنگاری را به‌طور خودکار نمی‌گیرد.

## ۵. Verification و Troubleshooting مفهومی

در اجرای آینده، ابتدا لایهٔ مسئله را مشخص کنید. وضعیت Process/Container، VM Guest و vNIC، یا Interface و جدول مسیر **VRF درست** را با ابزار پلتفرم و دسترسی مجاز بررسی کنید. فرمان Global `show ip route` ممکن است Context اشتباه باشد؛ دستگاه‌های مختلف برای نمایش Route داخل VRF نحو متفاوت دارند. سرویس Running بودن، مسیر دسترس‌پذیر بودن و پاسخ Application سه شاهد جدا هستند.

| مشاهده | فرضیهٔ مناسب | بررسی مفهومی بعدی |
|---|---|---|
| VM روشن، Guest به شبکه نمی‌رسد | vNIC/Virtual Switch، VLAN، Gateway یا Route | وضعیت Guest IP/route و نگاشت vNIC تا زیرساخت |
| Container اجرا می‌شود، Port از بیرون پاسخ نمی‌دهد | Bind address، Port mapping، Firewall یا Route | بررسی Listen داخل Container و انتشار Port/runtime policy |
| Tenant-A به Prefix خودش دسترسی ندارد | Interface در VRF اشتباه، Route/Next Hop یا ACL | VRF اختصاص‌یافته و جدول مسیر همان Context را بخوانید |
| A و B هر دو Prefix یکسان دارند | جست‌وجوی Route در Context اشتباه یا Leak ناخواسته | VRF/Interface binding و سیاست Route leaking را تطبیق دهید |
| Route وجود دارد ولی Application پاسخ ندارد | مسیر برگشت، ACL/Firewall، Host یا خود سرویس | شاهد دو سر و لایهٔ Application را جدا کنید |

هیچ فرمان یا خروجی واقعی این درس ثبت نشده است؛ جدول، مسیر بررسی را نشان می‌دهد نه علت قطعی.

## ۶. پرسش و پاسخ

1. **VM چیست؟** محیط مجازی دارای Guest OS با منابع ارائه‌شده توسط Hypervisor.
2. **Container معمول Kernel مستقل دارد؟** معمولاً از Kernel میزبان استفاده می‌کند؛ فناوری‌ها متفاوت‌اند.
3. **Container همیشه امن‌تر از VM است؟** چنین حکم مطلقی بدون طراحی و کنترل‌ها صحیح نیست.
4. **VRF چه چیزی را جدا می‌کند؟** جدول‌های Routing را در دستگاه پشتیبان به‌صورت منطقی.
5. **VRF یک ماشین مجازی است؟** خیر؛ مفهومی در Routing است.
6. **آدرس‌های هم‌پوشان در VRF ممکن‌اند؟** در طراحی مناسب، بله؛ ارتباط بین محیط‌ها نیازمند طراحی است.
7. **VRF به‌تنهایی رمزنگاری می‌کند؟** خیر، رمزنگاری و کنترل دسترسی جداگانه‌اند.
8. **چند VM روی یک Host یعنی منابع نامحدود است؟** خیر، منابع فیزیکی و سیاست تخصیص محدودیت دارند.
9. **سرویس Running است؛ مسیر VRF حتماً درست است؟** خیر، مسیر و سیاست مستقل بررسی می‌شوند.
10. **چرا نسخه و محصول پیش از کار عملی مهم است؟** قابلیت، نحو و شواهد به آن‌ها وابسته‌اند.
11. **آیا این کاربرگ VRF یا Container اجرا کرده است؟** خیر؛ طراحی تحلیلی است.
12. **Hypervisor چه نقشی دارد؟** مدیریت اجرای VM و تخصیص منابع مجازی بر اساس پلتفرم.

## واژه‌نامه و چک‌لیست

Hypervisor: مدیر VM؛ Guest OS: سیستم‌عامل داخل VM؛ Container: محیط اجرای ایزوله‌شدهٔ برنامه؛ Kernel: هستهٔ سیستم‌عامل؛ VRF: جدول‌های منطقی Routing مجزا.

- [ ] Guest Kernel و Kernel مشترک Container معمول را تفکیک می‌کنم.
- [ ] VRF را با VM و رمزنگاری یکی نمی‌دانم.
- [ ] کاربرگ مفهومی را اجرای واقعی گزارش نمی‌کنم.
