# CCNA SEC-05 — IPsec، Remote Access VPN و Site-to-Site VPN

**سطح:** CCNA. **پیش‌نیاز:** SEC-04 و IC-02. **هدف رسمی:** `5.5` توصیف IPsec VPN از راه دور و سایت‌به‌سایت. **وضعیت:** پیش‌نویس؛ سناریو طراحی‌شده و اجرا‌نشده؛ هیچ تونل واقعی برقرار نشده است.

## اهداف

تفاوت Remote Access و Site-to-Site را توضیح دهید، اجزای IPsec را نام ببرید و مسیر برقراری تونل را مرحله‌به‌مرحله تفسیر کنید.

## ۱. دو نوع VPN

**Site-to-Site VPN** معمولاً دو Gateway را برای اتصال Prefixهای دو سایت به‌هم متصل می‌کند؛ کاربران نهایی عموماً تونل Gateway-to-Gateway را جداگانه راه‌اندازی نمی‌کنند. **Remote Access VPN** یک Client/کاربر راه‌دور را به Gateway سازمان وصل می‌کند؛ IPsec با IKEv2 یکی از روش‌های Remote Access است و TLS-based VPN روش دیگری است. پس «Remote Access = SSL/TLS» و «IPsec فقط Site-to-Site است» هر دو نادرست‌اند. این درس به‌طور مشخص هر دو گونهٔ IPsec را می‌سنجد.

| ویژگی | IPsec Site-to-Site | IPsec Remote Access |
|---|---|---|
| نقطهٔ خاتمه | دو VPN Gateway | VPN Client/Endpoint و Gateway |
| طرف‌های احراز | معمولاً دو Gateway با PSK یا Certificate | Gateway و هویت Client/کاربر؛ روش دقیق محصول‌محور |
| دامنهٔ ترافیک | Prefixهای ثابت/تعریف‌شده در Traffic Selector و Policy | آدرس/Pool و Policy برای Client؛ ممکن است Split یا Full Tunnel باشد |
| مسیر کاربر | تونل زیرساختی معمولاً برای کاربر شفاف است | کاربر Client و پروفایل اتصال را به‌کار می‌برد |
| ریسک طراحی | Prefix overlap، Selector/Route/Return path | MFA/هویت، Client posture، Pool، Split Tunnel و دسترسی کمینه |

TLS VPN هم گزینهٔ Remote Access دیگری است، اما IPsec و TLS VPN پروتکل/سازوکار یکسانی نیستند. انتخاب به Clientها، سیاست، Gateway و نیاز سازمان بستگی دارد؛ هیچ‌یک به‌تنهایی مجوز دسترسی به همهٔ شبکه‌ها را نمی‌دهد.

## ۲. اجزای IPsec

- **AH** محرمانگی/رمزنگاری نمی‌دهد؛ می‌تواند یکپارچگی و احراز مبدأ را فراهم کند و مکانیزم ضدبازپخش آن به پیکربندی وابسته است.
- **ESP** می‌تواند محرمانگی، یکپارچگی/احراز مبدأ و ضدبازپخش فراهم کند؛ اینکه کدام خدمت فعال است به Proposal و پیکربندی بستگی دارد. در VPNهای رایج از ESP استفاده می‌شود.
- **IKE** برای تبادل کلید و توافق پارامترها؛ IKEv2 نسخهٔ جدیدتر است.
- **SA (Security Association)** مجموعهٔ یک‌طرفه‌ای از پارامترهای امنیتی، مانند الگوریتم‌ها، SPI و عمر کلید؛ برای دو جهت معمولاً SA جدا لازم است.

در **Transport Mode** (معمولاً Host-to-Host)، ESP از Payload محافظت می‌کند و سرآیند بیرونی IP باقی می‌ماند؛ AH پوشش متفاوتی دارد و می‌تواند یکپارچگی بخش‌هایی از سرآیند IP را نیز بررسی کند. در **Tunnel Mode**، بستهٔ IP اصلی در بستهٔ بیرونی جدید کپسوله می‌شود؛ این حالت برای Site-to-Site رایج است.

هر **IPsec SA یک‌طرفه** است؛ معمولاً دو SA برای دو جهت برقرار می‌شود. مراحل کلی: توافق IKE، احراز هویت دو طرف (PSK یا گواهی)، ایجاد SAهای لازم و انتقال داده. **PSK** برای لاب کوچک ساده است؛ در سازمان، مدیریت/چرخش راز مشترک دشوار می‌شود و گواهی مقیاس‌پذیری بهتری می‌دهد. PSK قوی ذاتاً الزاماً از گواهی ضعیف‌تر نیست؛ امنیت نهایی به طول راز، حفاظت کلید و پیکربندی بستگی دارد.

### مسیر بسته و Negotiation

```text
Site-to-Site: LAN-A ─ Gateway-A ══ IPsec/Internet ══ Gateway-B ─ LAN-B
Remote Access: Client ══ IPsec/IKEv2 ══ Gateway ─ Policy/Route ─ سازمان
```

در IKE، طرفین Proposalهای سازگار و روش احراز را توافق و SAهای لازم را برقرار می‌کنند؛ سپس Packetهای منطبق با Policy/Traffic Selector وارد ESP می‌شوند. برای دو جهت معمولاً SAهای یک‌طرفهٔ متناظر وجود دارد. تونل برقرار بودن، به‌تنهایی Route به LAN مقصد، Selector درست، مسیر برگشت، مجوز کاربر یا پاسخ Application را اثبات نمی‌کند. برای IKE معمولاً UDP/500 و در عبور از NAT، NAT Traversal می‌تواند UDP/4500 استفاده کند؛ فایروال/مسیر میانی و پشتیبانی محصول باید بررسی شود.

در Remote Access، **Split Tunnel** فقط Prefixهای منتخب را از VPN می‌فرستد و باقی ترافیک ممکن است از شبکهٔ محلی خارج شود؛ **Full Tunnel** مسیر بیشتری را به سازمان می‌برد. هر دو به Policy/DNS و امنیت Endpoint وابسته‌اند؛ Split Tunnel ذاتاً ناامن یا Full Tunnel ذاتاً کافی نیست. IPsec تونل را محافظت می‌کند، ولی MFA، وضعیت Endpoint، least-privilege و مجوز منابع لایهٔ جداگانه‌اند.

## ۴. Verification طراحی‌شده

**فرمان و خروجی آموزشی، اجرا‌نشده:**

```text
R1# show crypto ikev2 sa
IPv4 Crypto IKEv2  SA
Tunnel-id Local                 Remote                fvrf/ivrf            Status
1         198.51.100.1/500      203.0.113.1/500       none/none            READY
```

```text
R1# show crypto ipsec sa
interface: GigabitEthernet0/1
    Crypto map tag: VPN-MAP, local addr 198.51.100.1
    #pkts encaps: 0, #pkts decaps: 0
```

`READY` در این خروجی فرضی به حالت نشان‌داده‌شدهٔ IKE اشاره می‌کند؛ لفظ/ستون‌ها در IOS و نسخه‌های مختلف ممکن است فرق کنند. صفر بودن شمارندهٔ encaps/decaps فقط در همان لحظه یعنی Packet شمرده‌شده‌ای ثبت نشده؛ علت می‌تواند نبود ترافیک منطبق، Selector/ACL، Route/Return path، Policy/Counter موردنظر یا پلتفرم باشد. برای Verification مجاز، ابتدا مقدار قبل، یک ترافیک آزمایشی منطبق و مقصد مجاز، سپس مقدار بعد و مسیر دو سمت را مقایسه کنید. یک SA آماده به‌تنهایی عبور داده را اثبات نمی‌کند.

## ۵. کاربرگ مستقل تحلیلی و Troubleshooting

**طراحی‌شده و اجرا‌نشده؛** Objective `5.5` توصیفی است. کاربرگ زیر مقایسه و تحلیل Packet را تمرین می‌دهد؛ به معنی الزام پیکربندی یا اجرای تونل نیست. اگر بعداً به لاب اجرایی تبدیل شد، Image/Version, topology, credential handling, Console access و rollback باید جدا مشخص شوند. راز واقعی را در سند نگذارید.

**طرح:** Site-A `10.10.0.0/24`, Gateway-A `198.51.100.1`; Site-B `10.20.0.0/24`, Gateway-B `203.0.113.1`; کاربر دور Client-R `10.50.0.25` به Gateway سازمان وصل می‌شود. آدرس‌های Public از فضای مستنداتی‌اند، نه مقصد قابل استفاده در اینترنت.

1. روی نمودار، فرق دو Gateway site-to-site با یک Client و یک Gateway remote-access را مشخص کنید.
2. برای Site-to-Site، مسیر دوطرفهٔ هر Prefix را ترسیم و توضیح دهید Traffic Selector دو طرف باید با طرح مجاز سازگار باشد.
3. برای Remote Access، تعیین کنید Pool/Address، هویت کاربر، MFA/Device Policy، Route، DNS و اینکه Split یا Full Tunnel است کجا تعریف می‌شوند.
4. سه مشاهدهٔ جداگانه پیشنهاد دهید: IKE SA، شمارنده/SA دادهٔ ESP پس از ترافیک منطبق، و دسترسی Application از مبدأ مجاز. برای هرکدام بنویسید چه چیزی را **اثبات نمی‌کند**.
5. بدون ساخت راز یا ارسال Packet واقعی، Failure Matrix را حل کنید:

| نشانه | فرضیه‌های قابل بررسی، نه علت قطعی | شاهد بعدی |
|---|---|---|
| IKE برقرار نمی‌شود | مسیر/UDP 500/4500، Proposal و Lifetime، هویت/PSK/Certificate، ساعت در صورت اعتبارسنجی Certificate | لاگ/وضعیت هر دو Gateway و Policy؛ راز را در خروجی افشا نکنید |
| IKE آماده ولی ESP Counter صفر است | ترافیک آزمایشی تولید نشده، Selector/ACL منطبق نیست، Route یا Return path نیست | ترافیک مجاز و Counter/Route دو سمت را قبل/بعد مقایسه کنید |
| Counter بالا می‌رود ولی Application جواب ندارد | فیلتر بعد از تونل، Host firewall، NAT، سرویس مقصد یا Return path | Packet path/ACL و سلامت مقصد را مجاز بررسی کنید |
| Client وصل است ولی منابع خاص در دسترس نیستند | Split routes، DNS، Group/Identity Policy یا Prefix مجاز | جدول Route Client، Resolver و دسترسی به مقصدهای مجاز |

**پاسخ راهنما:** Site-to-Site به‌طور معمول Prefixهای دو طرف را میان Gatewayها محافظت می‌کند؛ Remote Access هویت/Policy کاربر و Client را نیز وارد می‌کند. Tunnel/IKE، ESP و Application سه سطح Verification جدا هستند. علت قطعی را بدون شاهد دو سر مسیر اعلام نکنید.

## ۶. سؤال‌ها و پاسخ

1. **Site-to-Site چیست؟** اتصال دو شبکه با تونل.
2. **Remote Access چیست؟** اتصال کاربر به شبکه.
3. **AH چه می‌دهد؟** یکپارچگی بدون رمزنگاری.
4. **ESP چه می‌دهد؟** می‌تواند رمزنگاری و یکپارچگی/احراز مبدأ را فراهم کند؛ ویژگی‌های دقیق به Proposal بستگی دارد.
5. **IKE چیست؟** تبادل کلید.
6. **SA چیست؟** توافق پارامترهای امنیتی.
7. **Tunnel Mode چه می‌کند؟** کل بسته را محصور می‌کند.
8. **Transport Mode چه می‌کند؟** در ESP، Payload را محافظت می‌کند و سرآیند بیرونی را نگه می‌دارد؛ AH پوشش متفاوتی دارد.
9. **PSK یا گواهی؟** گواهی معمولاً مدیریت مقیاس‌پذیرتری دارد؛ قوت نهایی به مدیریت راز/کلید و پیکربندی وابسته است.
10. **آیا IKEv2 خودبه‌خود تونل را امن می‌کند؟** خیر؛ نسبت به IKEv1 استاندارد جدیدتری است، اما امنیت به Proposal، احراز، مدیریت کلید، نسخه و پیکربندی بستگی دارد.
11. **چرا شمارنده صفر است؟** ممکن است ترافیک منطبق هنوز نرسیده باشد؛ Selector، ACL، Route، Return path و Counter درست را بررسی کنید.
12. **آیا این تونل اجرا شده است؟** خیر.

## واژه‌نامه و چک‌لیست

IPsec: مجموعهٔ امنیتی لایهٔ ۳؛ AH/ESP: هدرهای امنیتی؛ IKE: تبادل کلید؛ SA: توافق امنیتی؛ PSK: کلید مشترک.

- [ ] Site-to-Site و IPsec Remote Access را از هم و از TLS VPN تفکیک می‌کنم.
- [ ] ESP را با خدمات وابسته به Proposal می‌شناسم.
- [ ] وضعیت IKE، شمارندهٔ ESP و موفقیت Application را شاهدهای جداگانه می‌دانم.
- [ ] Route، Selector، Return path و Policy را بررسی می‌کنم؛ Tunnel را مجوز دسترسی کامل نمی‌گیرم.
- [ ] خروجی و سناریو را اجراشده معرفی نمی‌کنم.
