# CCNA AUT-03 — معماری SDN: Overlay، Underlay و Fabric

**سطح:** CCNA. **پیش‌نیاز:** AUT-02. **هدف رسمی:** `6.3` توصیف معماری Controller-Based و Software-Defined شامل Overlay، Underlay و Fabric. **وضعیت:** پیش‌نویس محتوایی؛ سناریوی PNETLab/Fabric در این درس طراحی‌شده و اجرا‌نشده است. در کاربرگ مستقل [AUT-03](academy-ccna-automation-03-sdn-fabric-lab-fa.md)، فقط Underlay ایزولهٔ Linux آزموده شد؛ ساخت VXLAN با Kernel حاضر ممکن نشد (`Error: Unknown device type.`). بنابراین هیچ Overlay، Fabric یا Controller اجرا/تأیید نشده است.

## اهداف

1. Underlay و Overlay را با مثال محسوس تفکیک کنید.
2. محاسبه کنید کپسوله‌سازی چقدر به MTU اضافه می‌کند و چه پیامدی دارد.
3. نقش **Border Node** و **Edge Node** را در Fabric توضیح دهید.
4. بفهمید چرا Fabric بدون Underlay سالم کار نمی‌کند.

## ۱. Underlay — شبکهٔ حامل

**Underlay** بستر IP است که بستهٔ بیرونیِ تونل را میان نقاط VTEP حمل می‌کند. این بستر می‌تواند از پیوندها و تجهیزات فیزیکی ساخته شود یا در لاب/Cloud بخشی مجازی داشته باشد؛ «فیزیکی» را با «لایهٔ ۲» یکی نگیرید. در طرح رایج Routed، Interfaceها، آدرس IP و مسیریابی میان VTEPها این کار را انجام می‌دهند.

ویژگی‌های Underlay خوب:

| ویژگی | چرا |
|---|---|
| **پایدار و قابل دسترس** | اختلال Underlay می‌تواند Overlay را مختل کند؛ پایداری و دسترسی بین VTEPها باید پایش شود |
| **قابل عیب‌یابی** | جداسازی مسئله‌های Underlay از Overlay مسیر بررسی را روشن‌تر می‌کند |
| **قابل پیش‌بینی، نه لزوماً تک‌مسیره** | ECMP ممکن است بسته‌ها را از چند مسیر معتبر عبور دهد؛ همهٔ مسیرها باید ظرفیت و MTU مناسب داشته باشند |
| **با سیاست روشن** | QoS، ACL و سیاست‌های دیگر ممکن است در Underlay هم اعمال شوند؛ محل هر سیاست و اثرش بر ترافیک تونل باید معلوم باشد |

**یک قاعدهٔ مهم:** Underlay **لازم نیست** لایهٔ ۲ باشد. در SD-Access، Underlay معمولاً یک شبکهٔ **Routed** (لایهٔ ۳) ساده است — فقط برای رساندن بستهٔ کپسوله‌شده از یک Edge به Edge دیگر. این برخلاف تصور رایج است که می‌گوید «Underlay باید L2 باشد».

## ۲. Overlay — شبکهٔ منطقی

**Overlay** شبکه‌ای منطقی است که روی Underlay ساخته می‌شود و آدرس‌دهی/توپولوژی سرویس را از پیوندهای فیزیکی جدا می‌کند؛ اما برای دسترسی، ظرفیت و MTU همچنان به Underlay وابسته است.

### VXLAN — نمونهٔ اصلی

VXLAN فریم Ethernet داخلی را (به‌جز FCS داخلی) در بستهٔ UDP/IP بیرونی کپسوله می‌کند:

```text
┌─────────────────────────────────────┐
│ Outer IP (Underlay)                 │
│  ┌───────────────────────────────┐  │
│  │ UDP (dst 4789)                │  │
│  │  ┌─────────────────────────┐  │  │
│  │  │ VXLAN Header (8 bytes)  │  │  │
│  │  │  VNI: 24-bit            │  │  │
│  │  │  ┌───────────────────┐  │  │  │
│  │  │  │ Original L2 Frame │  │  │  │
│  │  │  └───────────────────┘  │  │  │
│  │  └─────────────────────────┘  │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

| فیلد | مقدار | معنا |
|---|---|---|
| UDP destination port | **4789** | پورت مقصد استاندارد VXLAN |
| VNI | ۲۴ بیت | شناسهٔ شبکهٔ منطقی (فضای شناسه حدود **۱۶٫۸ میلیون**) |
| VTEP | — | نقطهٔ پایانی تونل (یک آدرس IP در Underlay) |

VNI یک شناسهٔ ۲۴ بیتی است؛ تعداد مقدارهای قابل‌استفاده به قواعد استاندارد و پیاده‌سازی وابسته است. در VLAN نیز مقدار ۱۲بیتی ۴۰۹۶ کد ممکن دارد، اما دامنهٔ VLANهای عادیِ قابل استفاده معمولاً ۱ تا ۴۰۹۴ است.

**چرا ۲۴ بیت VNI مهم است؟** VLAN فقط ۱۲ بیت دارد (۴۰۹۶ مقدار). سازمان‌های بزرگ به بیش از ۴۰۹۶ شبکهٔ منطقی نیاز دارند. VNI این محدودیت را حذف می‌کند.

**نکته**: دو فریم با همان VLAN ID در دو VNI مختلف می‌توانند هم‌زمان وجود داشته باشند و هیچ تداخلی ندارند — چون VNI مرز جدایی است.

## ۳. اثر کپسوله‌سازی بر MTU — با واحدهای روشن

**MTU لایه و پلتفرم مشخص می‌خواهد.** در این مثال منظور از 1500 بایت، **حداکثر اندازهٔ بستهٔ IP داخلی (inner IP MTU)** است؛ نه اندازهٔ کامل فریم Ethernet و نه طول فریم روی سیم. فرض‌ها: فریم داخلی بدون تگ VLAN، سربرگ Ethernet داخلی ۱۴ بایت، VXLAN روی UDP، و سربرگ بیرونی IPv4 بدون گزینه.

| بخشِ افزوده‌شده بیرون از بستهٔ IP داخلی | اندازه |
|---|---:|
| سربرگ Ethernet داخلی که در تونل حمل می‌شود | ۱۴ بایت |
| VXLAN | ۸ بایت |
| UDP | ۸ بایت |
| IPv4 بیرونی | ۲۰ بایت |
| **افزوده به بستهٔ IP داخلی** | **۵۰ بایت** |

بنابراین بستهٔ IPv4 بیرونی برابر است با **۱۵۰۰ + ۱۴ + ۸ + ۸ + ۲۰ = ۱۵۵۰ بایت**. این **طول بستهٔ IP بیرونی** است، نه اندازهٔ فریم «روی سیم». FCS فریم داخلی در VXLAN حمل نمی‌شود؛ فریم بیرونی روی هر لینک FCS خودش را می‌گیرد. بدون تگ بیرونی، فریم Ethernet بیرونی با ۱۴ بایت سربرگ و ۴ بایت FCS برابر ۱۵۶۸ بایت می‌شود؛ preamble/SFD و فاصلهٔ بین فریم‌ها در این عدد نیستند. اگر فریم داخلی VLAN-tagged باشد، تگ داخلی می‌تواند ۴ بایت دیگر به بستهٔ بیرونی بیفزاید. تگ بیرونی، برعکس، اندازهٔ فریم لایهٔ ۲ را تغییر می‌دهد، نه طول بستهٔ IP.

برای VXLAN روی IPv6، سربرگ بیرونی ثابت ۴۰بایتی است؛ با همین فرض‌های دیگر، بستهٔ IP بیرونی **۱۵۷۰ بایت** می‌شود. گزینه‌ها و سربرگ‌های اضافی نیز اندازه را تغییر می‌دهند. برخی راهنماهای Cisco سربار را به‌صورت خلاصه «۵۰ بایت» می‌نامند؛ هنگام تنظیم، تعریف MTU در همان مدل/نسخه و لایهٔ اندازه‌گیری را بررسی کنید.

RFC 7348 می‌گوید VTEPها نباید بستهٔ VXLAN را Fragment کنند؛ روترهای میانی ممکن است بستهٔ IPv4 بیرونی را Fragment کنند، ولی VTEP مقصد می‌تواند Fragmentها را دور بیندازد. Fragmentation در IPv6 توسط روتر میانی انجام نمی‌شود. بستهٔ بزرگ‌تر از MTU مسیر، بسته به IPv4/IPv6، DF، PMTUD و قابلیت محصول ممکن است با پیام MTU، Fragment میانی یا Drop روبه‌رو شود؛ Fragment را راه‌حل قابل اتکا فرض نکنید.

| راهکار | توضیح و محدودیت |
|---|---|
| **افزایش MTU مسیر Underlay** | مسیر کامل باید طول بستهٔ بیرونی را حمل کند؛ برای مثال، برای inner IP MTU=1500 در این فرض‌ها، حداقل IP MTU بیرونی 1550 در IPv4 یا 1570 در IPv6 لازم است. همهٔ لینک‌ها، تجهیزات و پلتفرم‌ها باید آن را پشتیبانی کنند. |
| **کاهش MTU داخلی** | با Underlay IPv4 MTU=1500، مقدار داخلی نزدیک 1450 می‌تواند سربار 50بایتی را جا دهد؛ سربرگ‌های داخلی اضافی و سیاست محصول را هم حساب کنید. |
| **TCP MSS clamping** | فقط اندازهٔ قطعه‌های TCP را محدود می‌کند؛ UDP، ICMP و فریم‌های غیر IP را حل نمی‌کند و جای تنظیم MTU/PMTUD را در همهٔ سناریوها نمی‌گیرد. |

برای آزمون، ابتدا MTU و مسیر کامل بین VTEPها را از مستندات و رابط‌ها بررسی کنید. در IOSهایی که `size` طول کل بستهٔ IPv4 (شامل سربرگ‌های IP و ICMP) را می‌گیرد، یک آزمون مفهومی چنین است:

```text
ping <remote-vtep-ip> size 1550 df-bit
```

نحو و معنای اندازه بین سیستم‌عامل‌ها و نسخه‌ها فرق دارد؛ مستند همان پلتفرم را بررسی کنید. موفقیت Ping با اندازهٔ 1500 فقط عبور یک بستهٔ IP بیرونی 1500بایتی را نشان می‌دهد و **به‌تنهایی** عبور ترافیک VXLAN با inner IP MTU=1500 را ثابت نمی‌کند. حتی Ping بزرگِ موفق نیز باید با شواهد و شمارنده‌های تونل و آزمون ترافیک واقعی تکمیل شود؛ فیلتر ICMP، نرخ‌دهی و مسیر نامتقارن هم می‌توانند نتیجه را تحت‌تأثیر بگذارند.

منابع فنی: [RFC 7348 §4.3 و §5](https://www.rfc-editor.org/rfc/rfc7348)؛ [راهنمای Cisco دربارهٔ VXLAN و MTU](https://www.cisco.com/c/en/us/support/docs/switches/nexus-9000-series-switches/118978-config-vxlan-00.html).

## ۴. Fabric — مجموعهٔ کل

**Fabric** اصطلاح چتر برای کل معماری است: Underlay + Overlay + کنترل + مرزها + سیاست.

### نقش‌های اصلی

| نقش | کار | مثال محسوس |
|---|---|---|
| **Control Plane Node** | محاسبهٔ توپولوژی و مسیر Overlay | LISP Map-Server در SD-Access |
| **Edge Node** | اتصال Endpointها (PC، AP، سرور) | سوییچ لایهٔ دسترسی |
| **Border Node** | اتصال Fabric به شبکه‌ها یا سرویس‌های بیرونی، طبق طراحی | سوییچی که به Core، WAN یا شبکهٔ خارج از Fabric وصل است |
| **Intermediate Node** | عبور ترافیک در Underlay | سوییچ میان Edge و Border |

### چرا Border لازم است؟

اگر همهٔ Edgeها به هم Overlay داشته باشند ولی هیچ‌کدام به بیرون وصل نباشند، **شبکه یک جزیره است**. Border Node نقش دروازه را دارد:

- ترافیک به اینترنت، دیتاسنتر قدیمی یا WAN از Border می‌رود.
- Border می‌تواند مسیرهای بیرونی، از جمله Default Route، را طبق طراحی و سیاست مسیریابی به Fabric متصل کند؛ Default Route در همهٔ توپولوژی‌ها الزامی نیست.
- برای دسترس‌پذیری بیشتر ممکن است چند Border و مسیر مستقل طراحی شود؛ تعداد و افزونگی تابع نیاز و معماری است، نه الزام همگانی.

**نکتهٔ طراحی:** تک‌مسیر بودن Edge تا Border می‌تواند نقطهٔ شکست واحد بسازد. مسیرهای جایگزین، همگرایی و رفتار شکست را در برابر نیاز دسترس‌پذیری بسنجید.

## ۵. جدول جمع‌بندی لایه‌ها

| لایه | نقش | نمونه | مسئولیت خطا |
|---|---|---|---|
| **Underlay** | رساندن بستهٔ بیرونیِ کپسوله‌شده | IP Routing، OSPF، IS-IS | مسیر/بستر انتقال؛ فیزیکی یا مجازی |
| **Overlay** | منطق، VNI، Policy | VXLAN + LISP | جداسازی و سیاست |
| **Fabric** | معماری کلی | SD-Access، ACI | همهٔ موارد |

**نکتهٔ مهم:** Flap یا از دست‌رفتن مسیری که VTEPهای درگیر به آن وابسته‌اند می‌تواند ترافیک Overlay روی همان مسیر را مختل کند؛ دامنهٔ اثر به توپولوژی، ECMP و همگرایی بستگی دارد. Underlay باید پایداری، MTU و دسترس‌پذیری لازم را فراهم کند. **Fabric سالم، Underlay قابل دسترس می‌خواهد.**

## ۶. سناریوی طراحی‌شده

**PNETLab مستقل، طراحی‌شده و اجرا‌نشده:** Underlay سه‌سوییچی با OSPF، Overlay فرضی VXLAN و یک Border Node. هیچ تونل VXLAN یا Fabric واقعی اجرا نشده است.

```text
                    ┌─── Border ─── [اینترنت]
                    │   10.0.0.1
                    │
        ┌───────────┴───────────┐
        │       Underlay        │
        │      OSPF Area 0      │
        └───────────┬───────────┘
                    │
       ┌────────────┴────────────┐
       │                         │
   [Edge-1]                  [Edge-2]
  10.0.0.11                 10.0.0.12
       │                         │
     PC-A                      PC-B
   192.168.10.10            192.168.10.11
```

| مؤلفه | آدرس | نقش |
|---|---|---|
| Border | `10.0.0.1` | خروج به بیرون |
| Edge-1، Edge-2 | `10.0.0.11`، `.12` | اتصال Endpoint |
| PC-A، PC-B | `192.168.10.10/24`، `.11/24` | همان VLAN منطقی، از راه دور |
| VNI | 10010 | شبکهٔ منطقی معادل VLAN 10 |
| Underlay MTU | طراحی: outer IP MTU برابر 1600 بایت | بیش از نیاز 1550بایتیِ مثال IPv4؛ تعریف MTU روی پلتفرم باید کنترل شود |

**انتظار طراحی:** PC-A و PC-B با وجود این‌که به دو Edge فیزیکی مختلف متصل‌اند، در VNI یکسان و یک **Broadcast Domain** منطقی قرار می‌گیرند و در صورت تکمیل پیکربندی و مسیرها می‌توانند به هم برسند. نمودار، Prefixهای Underlay را نشان نمی‌دهد؛ از آن نمی‌توان هم‌Subnet یا متفاوت‌بودن آن‌ها را نتیجه گرفت.

## ۷. کاربرگ مستقل PNETLab

**توضیح وضعیت:** عنوان PNETLab از قالب اولیهٔ تمرین حفظ شده، اما PNETLab/Controller در این محیط در دسترس نیست؛ مراحل زیر **طرح تحلیلیِ طراحی‌شده** هستند و اجرای Fabric واقعی محسوب نمی‌شوند. برای تمرین دارای توپولوژی/IP/فرمان‌های متناسب با Platform، بررسی مرحله‌ای و گزارش آزمون Underlay/VXLAN در Linux به [کاربرگ مستقل AUT-03](academy-ccna-automation-03-sdn-fabric-lab-fa.md) مراجعه کنید. در Sandbox حاضر Underlay آزموده شد، ولی Kernel ساخت VXLAN را نپذیرفت؛ Controller و Overlay اجرا نشده‌اند.

1. یک Underlay ساده با سه سوییچ و OSPF طراحی کنید و در صورت داشتن Image مجاز، دسترسی Loopbackها را بررسی کنید.
2. نسخهٔ Image و تعریف/مقدار MTU رابط‌ها و مسیر را از فرمان مستندشدهٔ همان پلتفرم ثبت کنید؛ `show interfaces` فقط نمونه‌ای وابسته به IOS است.
3. اگر پلتفرم از آزمون IPv4 با DF پشتیبانی می‌کند، بین دو آدرس VTEP اندازهٔ **بستهٔ IP بیرونی** را تا ۱۵۵۰ بایت آزمایش کنید؛ نحو و معنای `size` را در همان نسخه بیابید. پاسخ ICMP به‌تنهایی اثبات کافی نیست.
4. با فرض inner IP MTU=1500، فریم داخلیِ بدون VLAN و VXLAN روی IPv4، نیاز MTU بیرونی را حساب کنید: ۱۵۰۰ + ۱۴ + ۸ + ۸ + ۲۰ = ۱۵۵۰ بایت. برای IPv6 در همین فرض، ۱۵۷۰ بایت است.
5. یک Border Node و مسیرهای واقعی/فرضی به بیرون را روی نمودار مشخص کنید؛ Default Route را فقط اگر در توپولوژی وجود دارد اضافه کنید.
6. سناریوی از دست‌رفتن یکی از مسیرهای Underlay را طراحی و دامنهٔ اثر و همگرایی را تحلیل کنید.
7. یک طرح افزونگی Border رسم و مزیت و هزینه/محدودیت آن را با نیاز دسترس‌پذیری مقایسه کنید.

هیچ‌کدام اجرا نشده و هیچ اندازه‌گیری واقعی ثبت نشده است.

## ۸. سؤال‌ها و پاسخ

1. **Underlay چیست؟** بستر IP/انتقالی که بستهٔ بیرونی را میان VTEPها می‌رساند؛ غالباً Routed است و می‌تواند اجزای فیزیکی یا مجازی داشته باشد.

2. **Overlay چیست؟** شبکهٔ منطقی روی Underlay با VNI و Policy مستقل.

3. **Underlay حتماً L2 است؟** نه. معمولاً در SD-Access یک شبکهٔ Routed لایهٔ ۳ است.

4. **VXLAN چه چیزی را کپسوله می‌کند؟** فریم Ethernet داخلی را در UDP/IP بیرونی؛ FCS داخلیِ فریم در کپسوله‌سازی حمل نمی‌شود.

5. **VNI چند بیت است؟** ۲۴ بیت، تا حدود ۱۶ میلیون شبکهٔ منطقی.

6. **VXLAN از چه پورتی استفاده می‌کند؟** UDP 4789.

7. **برای inner IP MTU برابر ۱۵۰۰، اندازهٔ بستهٔ IPv4 بیرونی در فرض این درس چقدر است؟** ۱۵۵۰ بایت: بستهٔ داخلی ۱۵۰۰ + سربرگ Ethernet داخلی ۱۴ + UDP هشت + VXLAN هشت + IPv4 بیرونی ۲۰. این طول بستهٔ IP است، نه کل فریم روی سیم.

8. **اگر Underlay IP MTU برابر ۱۵۰۰ باشد، آیا inner IP MTU=1500 تضمین می‌شود؟** خیر؛ بستهٔ بیرونیِ ۱۵۵۰ از MTU مسیر بزرگ‌تر است. VTEP آن را Fragment نمی‌کند؛ پیام PMTU یا Drop محتمل است و رفتار Fragment روتر میانی/دورریزی مقصد به نسخه و IP بستگی دارد. MTU مسیر را افزایش دهید یا MTU داخلی/تنظیمات را با طرح درست کاهش دهید؛ MSS فقط TCP را محدود می‌کند.

9. **آزمون اندازهٔ بزرگ چه چیزی را ثابت می‌کند؟** Ping با DF و اندازهٔ تفسیرشده طبق همان CLI می‌تواند عبور یک بستهٔ بیرونی تا آن اندازه را بررسی کند. `size 1500` لزوماً پشتیبانی از inner MTU=1500 را ثابت نمی‌کند؛ ICMP filtering و سایر محدودیت‌ها هم نتیجه را مبهم می‌کنند.

10. **Border Node چیست؟** نقطهٔ اتصال Fabric به بیرون (اینترنت، Core، WAN).

11. **Edge Node چیست؟** نقطهٔ اتصال Endpointها به Fabric.

12. **اگر مسیر Underlay میان VTEPها قطع شود چه می‌شود؟** ترافیک Overlay که به آن مسیر وابسته است ممکن است مختل شود؛ دامنهٔ اثر به مسیرهای جایگزین و همگرایی بستگی دارد.

## واژه‌نامه و چک‌لیست

**Underlay**: بستر IP/انتقالی؛ **Overlay**: شبکهٔ منطقی؛ **VXLAN**: کپسوله‌سازی L2 در UDP؛ **VNI**: شناسهٔ ۲۴ بیتی شبکهٔ منطقی؛ **VTEP**: نقطهٔ پایانی تونل؛ **Fabric**: معماری کامل؛ **Border Node**: مرز بیرونی؛ **Edge Node**: اتصال Endpoint؛ **MTU**: حداکثر اندازهٔ بسته.

- [ ] Underlay و Overlay را با مثال تفکیک می‌کنم.
- [ ] می‌دانم Underlay لازم نیست L2 باشد.
