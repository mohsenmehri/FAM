# CCNA IS-02 — NTP در حالت Client و Server

**سطح:** CCNA. **پیش‌نیاز:** NF-08 و IC-01. **هدف رسمی:** `4.2` پیکربندی و Verification NTP در حالت Client و Server. **وضعیت:** پیش‌نویس؛ فرمان‌ها و خروجی‌ها طراحی‌شده و اجرا‌نشده‌اند؛ مدل و نسخهٔ IOS انتخاب نشده است.

## اهداف

نقش NTP را توضیح دهید، یک روتر را به‌عنوان Client و روتر دیگر را Server پیکربندی کنید و همگام بودن ساعت را Verification کنید.

## ۱. چرا NTP؟

زمان دقیق و یکسان برای Log، گواهی، Kerberos، هم‌بستگی رویدادها و عیب‌یابی ضروری است. **NTP** ساعت دستگاه‌ها را با منبع مرجع همگام می‌کند. ساعت داخلی روتر **Clock** است؛ بدون NTP، ساعت‌های دستگاه‌ها با هم اختلاف پیدا می‌کنند و مقایسهٔ Logها بی‌معنا می‌شود. `show clock` ساعت محلی و `show ntp status` وضعیت همگامی را نشان می‌دهد.

NTP از **Stratum** برای نشان‌دادن فاصلهٔ منطقی از منبع مرجع استفاده می‌کند.

| Stratum | معنا | مثال |
|---|---|---|
| **0** | منبع مرجع فیزیکی (ساعت اتمی، GPS) — در بستهٔ NTP دیده نمی‌شود | Atomic Clock |
| **1** | مستقیماً به Stratum 0 متصل | سرور NTP با GPS |
| **2** | از Stratum 1 زمان می‌گیرد | سرور سازمانی |
| **3 و بالاتر** | هر مرحله یک واحد دورتر | روترها و کلاینت‌ها |
| **16** | **همگام نیست (Unsynchronized)** | ساعت معتبر نیست |

**نکتهٔ عملی مهم:** Stratum **کیفیت نیست، فاصله است.** یک سرور Stratum 3 می‌تواند از Stratum 2 دقیق‌تر باشد اگر مسیر شبکه‌اش پایدارتر باشد. عدد کوچک‌تر، «دسترسی کوتاه‌تر به مرجع» را نشان می‌دهد، نه «کیفیت بالاتر».

**Stratum 16 = همگام‌نشده.** اگر در `show ntp status` عدد 16 دیدید، ساعت معتبر نیست حتی اگر ساعت نمایش داده شود. این یکی از رایج‌ترین اشتباهات خواندن خروجی است.

**Client** از Server زمان می‌گیرد و **Server** زمان را ارائه می‌دهد. روتر می‌تواند هم‌زمان Client یک منبع و Server برای دستگاه‌های دیگر باشد.

## ۲. سناریوی دو روتر

**PNETLab مستقل، طراحی‌شده و اجرا‌نشده:** R1 به‌عنوان NTP Server با آدرس `192.0.2.1/24` و R2 به‌عنوان Client با آدرس `192.0.2.2/24`. R1 ساعت خود را از یک منبع بالادست فرضی می‌گیرد؛ در آزمایشگاه ایزوله می‌توان ساعت را دستی تنظیم کرد. نام تصویر و نسخهٔ IOS تأیید نشده‌اند.

## ۳. پیکربندی پیشنهادی

**فرمان‌ها اجرا‌نشده‌اند.** روی R1:

```text
configure terminal
clock timezone TRT 3
ntp server 192.0.2.100
end
```

روی R2:

```text
configure terminal
clock timezone TRT 3
ntp server 192.0.2.1
end
```

در لاب ایزوله‌ای که R1 **هیچ منبع بالادست معتبری ندارد**، ساعتش را در صورت نیاز دستی تنظیم کنید و به‌جای `ntp server 192.0.2.100` از `ntp master 3` فقط به‌عنوان منبع آزمایشگاهی استفاده کنید؛ این منبع، زمان معتبر بیرونی را تضمین نمی‌کند.

| فرمان | معنای **دقیق** |
|---|---|
| `ntp master 3` | روتر را منبع معتبر/authoritative با Stratum 3 معرفی می‌کند، حتی اگر با منبع بیرونی همگام نشده باشد؛ اگر منبع معتبر دیگری در دسترس باشد، این فرمان ممکن است بر انتخاب منبع اثر بگذارد. |
| `ntp server 192.0.2.1` | ساعت این روتر را برای همگام‌شدن با آن سرور تنظیم می‌کند؛ روترِ همگام می‌تواند برای دستگاه‌های پایین‌دست هم زمان فراهم کند. |
| `ntp server 192.0.2.1 prefer` | در صورت وجود چند منبع، این یکی ترجیح داده می‌شود |

**دام بزرگ:** `ntp master` فرمان همگام‌سازی با سرور نیست؛ دستگاه را حتی بدون منبع بیرونیِ همگام‌شده به منبع authoritative تبدیل می‌کند و ممکن است منبع معتبر را تحت‌تأثیر قرار دهد. برای R1 که باید از `192.0.2.100` زمان بگیرد، در این نمونه فقط `ntp server` را تنظیم کنید؛ `ntp master` را به سناریوی ایزوله و آموزشی محدود کنید و مستندات نسخهٔ هدف را بخوانید.

برای کاهش پذیرش زمان از منبع ناشناس/جعل‌شده، IOSهای پشتیبان می‌توانند از `ntp authentication-key` و `ntp trusted-key` استفاده کنند؛ گیرنده باید کلید و منبع مورد انتظار را درست تنظیم کند. این احراز، همهٔ حمله‌های NTP یا جعل مسیر را خنثی نمی‌کند و نحو/قابلیت آن به نسخه وابسته است. بدون اعتبارسنجی منبع، زمان نادرست می‌تواند روی گواهی TLS، Kerberos، Log و پشتیبان‌گیری اثر بگذارد.

## ۴. Verification

**فرمان و خروجی آموزشی، اجرا‌نشده:**

```text
R2# show ntp status
Clock is synchronized, stratum 4, reference is 192.0.2.1
nominal freq is 250.0000 Hz, actual freq is 250.0001 Hz, precision is 2**10
```

`synchronized` یعنی همگام‌سازی انجام شده؛ `stratum` فاصلهٔ منطقی از مرجع را نشان می‌دهد. فرمان `show ntp associations` منبع و وضعیت آن را نشان می‌دهد. همهٔ این خروجی‌ها طراحی‌شده‌اند و در محیط واقعی ثبت نشده‌اند.

## ۵. کاربرگ مستقل PNETLab — NTP Client/Server

**هدف رسمی `4.2`:** یک دستگاه را در نقش Server/منبع و دیگری را به‌عنوان Client پیکربندی و همگامی را Verification کنید. **این سناریو طراحی‌شده و اجرا‌نشده است.** دو روتر IOSv/IOL با Console و یک Ethernet link کافی است؛ هیچ مسیر بیرونی لازم نیست.

```text
R1 Gi0/0 192.0.2.1/24  (NTP lab source, stratum 3)
        ───────────── SW-LAB ─────────────
R2 Gi0/0 192.0.2.2/24  (NTP client)
```

پیش از شروع Image/نسخه، Interface، ساعت اولیه و دسترسی UDP/123 را ثبت و Snapshot بگیرید. در این لاب ایزوله R1 را فقط به‌عنوان **منبع مصنوعی آزمایشگاهی** تنظیم کنید؛ `ntp master 3` زمان معتبر جهانی ایجاد نمی‌کند و نباید جایگزین منبع سازمانی شود. اگر IOS مقصد پیکربندی متفاوتی دارد، Command Reference همان نسخه مقدم است.

### اجرا و Verification

1. به R1 و R2 آدرس‌های جدول بالا بدهید و با `show ip interface brief` و Ping مجاز، اتصال پایه را جداگانه تأیید کنید.
2. فقط در همین لاب، در R1 ساعت آزمون را در صورت نیاز با `clock set 12:00:00 20 NOV 2026` تنظیم کنید؛ سپس `ntp master 3` را فعال کنید. در R2، `ntp server 192.0.2.1` را قرار دهید. `clock timezone` فقط نحوهٔ نمایش محلی را عوض می‌کند، نه زمان UTC دریافتی.
3. در هر دو روتر `show clock detail`, `show ntp status`, `show ntp associations` (یا فرم پشتیبانی‌شدهٔ همان نسخه) را ثبت کنید. R2 ممکن است برای Poll و رسیدن به حالت synchronized زمان بخواهد؛ خروجی و زمان دقیق نسخه‌وابسته است. Stratumِ Client معمولاً از منبع یک واحد بیشتر است؛ `stratum 16` یا `unsynchronized` همگامی معتبر نیست.
4. ساعت R2 را در صورت نیاز فقط روی روتر آزمایشگاهی با `clock set` تغییر دهید و رفتار تدریجی/تنظیم زمان را ثبت کنید؛ NTP همیشه ساعت را یکباره جلو/عقب نمی‌برد.
5. **نقص کنترل‌شده:** رابط R1 را موقتاً Shutdown کنید یا لینک را قطع کنید؛ وضعیت Association و زمان از دست‌رفتن همگامی را در R2 مشاهده کنید. Listener و لینک را برگردانید و پس از Pollهای بعدی، بازگشت همگامی را بررسی کنید. زمان تشخیص را حدس نزنید.
6. پس از آزمایش، Snapshot را بازیابی یا لینک/ساعت/سیاست را به حالت اولیه برگردانید. از `ntp master` در شبکهٔ عملیاتی بدون طراحی منبع مرجع استفاده نکنید.

| نشانه | بررسی مرحله‌ای |
|---|---|
| Server دیده نمی‌شود | آدرس R1، مسیر، UDP/123، Source Interface و ساعت/وضعیت NTP سرور |
| Association هست اما Sync نیست | Reach/Stratum/زمان، دسترسی دوطرفه، Poll interval و اختلاف ساعت؛ خروجی همان IOS را بخوانید |
| R2 روی Stratum 16 مانده | منبع انتخاب‌شده معتبر/قابل دسترس نیست؛ فقط تنظیم ساعت محلی، Sync را ثابت نمی‌کند |
| زمان محلی سه ساعت جابه‌جاست | UTC در برابر Time Zone و DST را تفکیک کنید؛ Time Zone NTP را تغییر نمی‌دهد |
| پس از بازیابی فوراً Sync نیست | چند چرخهٔ Poll صبر کنید و Association/Reach را دوباره ثبت کنید؛ نتیجهٔ فوری تضمین نمی‌شود |

**شواهد تحویل:** نسخهٔ IOS و توپولوژی، پیکربندی Server/Client، خروجی‌های پیش و پس از Sync، نقص/بازیابی و محدودیت منبع مصنوعی ثبت شده باشد. خروجی‌های متن درس نمونه‌اند؛ هنوز هیچ IOS/PNETLab اجرا نشده است.

## ۶. سؤال‌ها و پاسخ

1. **NTP چه می‌کند؟** همگام‌سازی ساعت.
2. **Stratum چیست؟** فاصلهٔ منطقی از منبع مرجع.
3. **Stratum 1 یعنی چه؟** اتصال مستقیم به منبع مرجع.
4. **Client چیست؟** دستگاهی که زمان می‌گیرد.
5. **Server چیست؟** دستگاهی که زمان ارائه می‌دهد.
6. **`show ntp status` چه نشان می‌دهد؟** وضعیت همگامی.
7. **`ntp master` چه می‌کند؟** دستگاه را به‌عنوان منبع معرفی می‌کند.
8. **چه پورتی استفاده می‌شود؟** UDP 123.
9. **چرا زمان یکسان مهم است؟** Log، گواهی و عیب‌یابی.
10. **آیا احراز هویت NTP ممکن است؟** بله با کلید.
11. **یک روتر هم‌زمان Client و Server است؟** بله.
12. **آیا این سناریو اجرا شده است؟** خیر.

## واژه‌نامه و چک‌لیست

NTP: پروتکل زمان؛ Stratum: لایهٔ فاصله؛ Client: گیرندهٔ زمان؛ Server: دهندهٔ زمان؛ Synchronized: همگام.

- [ ] ساعت همهٔ دستگاه‌ها را یکسان می‌کنم.
- [ ] Stratum را با فاصله از مرجع تفسیر می‌کنم.
- [ ] همگامی را با `show ntp status` تأیید می‌کنم.
