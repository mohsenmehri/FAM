# CCNA NF-13 — بررسی پارامترهای IP در Windows، macOS و Linux

**سطح:** CCNA. **پیش‌نیاز:** NF-09 و NF-11؛ آشنایی عمومی با خط فرمان. **هدف رسمی مرتبط:** `1.10`، فعل Verify IP parameters for Client OS. **بازبینی متنی ۲۰۲۶-۱۱-۲۰:** فرمان‌ها و کاربرگ سه سیستم‌عامل بازخوانی شدند؛ هدف عملی تا اجرای Verify روی Windows، macOS و Linux و ثبت خروجی واقعی باز است. **وضعیت:** همهٔ فرمان‌ها و خروجی‌ها پیشنهادی و اجرا‌نشده‌اند؛ نسخه‌های سیستم‌عامل انتخاب یا تأیید نشده‌اند. دستورها فقط در Client آزمایشی مستقل و مجاز بررسی شوند.

## هدف

آدرس، Prefix/Mask، Default Gateway و DNS گزارش‌شدهٔ کلاینت را در سه سیستم‌عامل بررسی کنید؛ تفاوت مشاهدهٔ پیکربندی با اثبات سلامت سرویس را توضیح دهید و شواهد بدون اطلاعات محرمانه ثبت کنید.

## ۱. پارامترهایی که باید بخوانیم

| پارامتر | معنی | مشاهدهٔ آن چه چیزی را ثابت نمی‌کند؟ |
|---|---|---|
| IP و Prefix/Mask | آدرس و محدودهٔ رابط | درست بودن مسیر یا پاسخ سرویس |
| Default Gateway | مسیر عمومی برای مقصدهای فاقد مسیر اختصاصی مناسب | دسترسی به اینترنت یا سالم بودن Gateway |
| DNS Server | آدرس Resolver پیکربندی‌شده | موفق بودن حل نام یا سلامت سرویس مقصد |
| وضعیت رابط | گزارش فعال‌بودن دستگاه/لینک | صحت همهٔ VLANها، مسیرها و برنامه‌ها |

اگر چند رابط، VPN یا چند مسیر وجود داشته باشد، وجود یک Default Gateway به‌تنهایی تعیین‌کنندهٔ مسیر همهٔ مقصدها نیست. جدول مسیر و انتخاب رابط را نیز بررسی کنید.

## ۲. Windows

**فرمان‌های مشاهده‌ای پیشنهادی، اجرا‌نشده:**

```text
ipconfig /all
route print -4
nslookup example.com
```

`ipconfig /all` جزئیات رابط‌ها از جمله آدرس، ماسک، Gateway و DNS گزارش‌شده را نشان می‌دهد. `route print -4` جدول مسیر IPv4 را نمایش می‌دهد. `nslookup` یک پرس‌وجوی نام انجام می‌دهد و به Resolver و اتصال مجاز نیاز دارد؛ پاسخ ممکن است تغییر کند یا در شبکهٔ ایزوله وجود نداشته باشد.

**نمونهٔ آموزشی و کوتاه‌شده، اجرا‌نشده:**

```text
IPv4 Address. . . . . . . . . . . : 192.168.10.10
Subnet Mask . . . . . . . . . . . : 255.255.255.0
Default Gateway . . . . . . . . . : 192.168.10.1
DNS Servers . . . . . . . . . . . : 192.168.10.53
```

این خروجی فرضی یک کلاینت `/24`، Gateway و DNS را نشان می‌دهد؛ رابط صحیح و وضعیت واقعی باید در همان محیط بررسی شوند.

## ۳. Linux

**فرمان‌های پیشنهادی، اجرا‌نشده:**

```bash
ip -br address
ip route
resolvectl status
# fallback for systems without systemd-resolved:
cat /etc/resolv.conf
```

`ip -br address` رابط‌ها و Prefix را خلاصه می‌کند؛ `ip route` مسیرهای IPv4 را نشان می‌دهد. `resolvectl status` تنظیمات Resolver و لینک‌های فعال را در سیستم دارای systemd-resolved نمایش می‌دهد؛ در نبود آن، `nmcli device show` یا `/etc/resolv.conf` را متناسب با توزیع بررسی کنید. این فایل ممکن است Stub محلی را نشان دهد، نه Resolver بالادستی.

**نمونهٔ آموزشی، اجرا‌نشده:**

```text
enp0s3  UP  192.168.10.10/24
default via 192.168.10.1 dev enp0s3
```

نام رابط فرضی است. `/24` Prefix و `via` در خط مسیر، Gateway آن مسیر را نشان می‌دهد. این دو خط متعلق به دو فرمان متفاوت‌اند، نه یک خروجی واحد.

## ۴. macOS

**فرمان‌های پیشنهادی، اجرا‌نشده؛** نام رابط و Service متناسب با دستگاه و نسخه تغییر می‌کند:

```text
ifconfig
route -n get default
netstat -rn -f inet
scutil --dns
networksetup -listallnetworkservices
```

`ifconfig` آدرس و وضعیت رابط‌ها، `route -n get default` مسیر پیش‌فرض انتخاب‌شده، `netstat -rn -f inet` جدول مسیر IPv4، و `scutil --dns` پیکربندی Resolverهای DNS را نشان می‌دهند. نام Network Service را با `networksetup -listallnetworkservices` پیدا کنید؛ `en0` را بدون بررسی حدس نزنید. چند Resolver یا رابط ممکن است وجود داشته باشد؛ باید مورد مربوط به مسیر و نام هدف بررسی شود. بدون نسخه و محیط واقعی، شکل دقیق خروجی و ترتیب Resolverها تضمین نمی‌شود.

## ۵. کاربرگ مستقل — بررسی IP در سه سیستم‌عامل Client

**هدف رسمی `1.10`:** Verify کردن پارامترهای IP در Windows، macOS و Linux. **طراحی‌شده و اجرا‌نشده.** این کاربرگ به Client OS واقعی/VM نیاز دارد؛ VPCS در PNETLab جایگزین Windows/macOS/Linux نیست. اگر محیط PNETLab به Cloud/host-only متصل می‌شود، شبکهٔ host-only را اختصاصی و جدا از NIC اینترنت/شبکهٔ سازمانی بسازید. نام Cloud، Hypervisor، نسخه و نحوهٔ اتصال را پیش از اجرا ثبت کنید. macOS فقط روی سخت‌افزار/مجازی‌سازی مجاز برای آن سیستم‌عامل به‌کار رود؛ PNETLab خودش macOS را شبیه‌سازی نمی‌کند.

### توپولوژی و برنامهٔ آدرس‌دهی

```text
Windows VM ─┐
Linux VM ────┼── isolated host-only / PNETLab Cloud ─ SW-LAB ─ R1 Gi0/0
macOS host ─┘                                                  10.77.10.1/24
```

| گره | پارامتر مورد انتظار | توضیح |
|---|---|---|
| R1 Gi0/0 | `10.77.10.1/24` | DHCP Server محلی، بدون WAN/Default Route |
| Windows/Linux/macOS Client | DHCP lease `10.77.10.100–150/24` | هر OS را جداگانه به همان LAN آزمایش متصل کنید؛ آدرس باید یکتا باشد |
| هر Client | Default Gateway `10.77.10.1` | وجود آن فقط صحت تنظیم را نشان می‌دهد، نه دسترسی بیرون |
| هر Client | DNS Server `10.77.10.53` | **آدرس آزمایشیِ پیکربندی‌شده؛ سرویس DNS در این لاب فراهم نیست** مگر Resolver جداگانه‌ای اضافه و ثبت شود |

R1 نمونهٔ IOS (فرمان‌ها اجرا‌نشده و نسخه‌وابسته):

```text
configure terminal
interface GigabitEthernet0/0
 ip address 10.77.10.1 255.255.255.0
 no shutdown
exit
ip dhcp excluded-address 10.77.10.1 10.77.10.99
ip dhcp excluded-address 10.77.10.151 10.77.10.254
ip dhcp pool CLIENTS
 network 10.77.10.0 255.255.255.0
 default-router 10.77.10.1
 dns-server 10.77.10.53
end
```

این تنظیم فقط DHCP را روی Interface داخل لاب ارائه می‌کند؛ DHCP Server واقعی روی Router باید در Image انتخاب‌شده پشتیبانی شود. Router مسیر بالادست ندارد، و هیچ DNS Server در `.53` ساخته نشده است. بنابراین این تمرین **وجود پارامتر DNS** را بررسی می‌کند، نه پاسخ DNS، Routing اینترنت یا دسترسی سرویس. هیچ DHCP/VM واقعاً راه‌اندازی نشده است.

### مراحل مشاهده و Verification

1. شبکهٔ ایزوله، Snapshot، مجوز و Version هر Client را ثبت کنید؛ قبل از وصل کردن Cloud مطمئن شوید اتصال به NAT/Bridge عمومی یا شبکهٔ تولیدی ندارد.
2. R1 را فقط در لاب پیکربندی کنید. با `show ip interface brief` وضعیت رابط و با `show ip dhcp pool` و `show ip dhcp binding`، در صورت پشتیبانی، Pool و Leaseها را بررسی کنید.
3. هر OS را جداگانه به LAN وصل کنید و با فرمان‌های §۲–۴ این موارد را ثبت کنید: رابط فعال، IPv4/Prefix یا Mask، DHCP/Lease اگر گزارش می‌شود، Gateway/route و DNS Resolver. از هر دستگاه خروجی واقعی، زمان، Version و نام رابط را ثبت کنید؛ قبل از اشتراک‌گذاری نام/شناسه‌های حساس را حذف کنید.
4. نتیجهٔ مورد انتظار هر Client: یک IP یکتا از `10.77.10.100–150`, Prefix `/24` (Mask `255.255.255.0`), مسیر پیش‌فرض از `10.77.10.1`, و DNS پیکربندی‌شدهٔ `10.77.10.53`. ترتیب یا قالب خروجی‌ها بین OSها متفاوت است.
5. `ping 10.77.10.1` را فقط اگر سیاست OS/فایروال پاسخ ICMP می‌دهد، به‌عنوان یک آزمون اتصال محدود اجرا کنید. موفقیت Ping یا وجود Default Route اثبات DNS/Internet نیست. `nslookup`/`dig` روی `.53` در این لاب انتظار پاسخ ندارد؛ این عدم پاسخ نشان‌دهندهٔ نبود Resolver آزمایشی است، نه پیکربندی نادرست DNS Server address.
6. **نقص کنترل‌شده:** در لاب، `default-router` Pool را موقتاً به `10.77.10.254` تغییر دهید؛ Lease یک Client را با روش مجاز و متناسب با OS تازه کنید. در جدول Route/پارامترهای Client وجود Gateway اشتباه را تشخیص دهید؛ Ping احتمالی به Gateway نباید به‌تنهایی نتیجه‌گیری کند. تنظیم Pool را به `.1` برگردانید، Lease را دوباره تازه کنید و مقدار مورد انتظار را Verification کنید. تجدید Lease می‌تواند اتصال را قطع کند؛ این کار را فقط در Client ایزوله انجام دهید.
7. خروجی‌ها را با برنامهٔ آدرس‌دهی مقایسه و وضعیت آزمون، نقص، بازیابی و موارد نامشخص را ثبت کنید. هیچ تغییر/`release`/Reconnect روی رابطی که از راه دور یا تولیدی استفاده می‌شود انجام ندهید.

**معیار موفقیت/شواهد:** برای هر سه سیستم‌عامل، نام و Version، فرمان دقیق، خروجی پاک‌سازی‌شده، رابط مربوط، IPv4/Prefix، مسیر پیش‌فرض و DNS ثبت شود؛ سه پارامتر با نقشه مقایسه شوند؛ نقص Gateway تشخیص و پس از اصلاح دوباره Verify شود؛ وضعیت سرویس DNS از صرفاً آدرس Resolver جدا بماند. اجرای واقعی در این نسخه ثبت نشده است.

## ۶. عیب‌یابی

| مشاهده | بررسی | پرهیز |
|---|---|---|
| IP مورد انتظار نیست | رابط، روش تخصیص، DHCP و نسخه | تنظیم دستی روی شبکهٔ عملیاتی بدون مجوز |
| IP وجود دارد اما نام حل نمی‌شود | DNS، مسیر Resolver و پیام پرس‌وجو | یکی‌گرفتن مشکل نام با قطعی کامل شبکه |
| چند Default Route هست | اولویت و مسیر مقصد و رابط | فرض استفاده از اولین خط دیده‌شده |
| Link-Local IPv6 دیده می‌شود | دامنهٔ لینک و آدرس‌های دیگر را بررسی کنید | نتیجه‌گیری از آن دربارهٔ دسترسی اینترنت |

## ۷. سؤال‌ها با پاسخ

1. **`ipconfig /all` چه می‌دهد؟** جزئیات گزارش‌شدهٔ رابط‌ها؛ سلامت سرویس را تضمین نمی‌کند.
2. **آدرس IPv4 دارد؛ DNS قطعاً سالم است؟** خیر، Resolver و پرس‌وجو باید جداگانه بررسی شوند.
3. **Linux `/etc/resolv.conf` آدرس localhost دارد؛ سرور بالادستی چیست؟** از این مشاهده به‌تنهایی معلوم نیست؛ ممکن است Stub محلی باشد.
4. **در macOS از چه فرمانی برای Resolver استفاده می‌کنیم؟** `scutil --dns` به‌صورت پیشنهادی و وابسته به نسخه.
5. **`ip route` چه نشان می‌دهد؟** جدول مسیر IPv4 گزارش‌شده در Linux.
6. **دو رابط فعال‌اند؛ کدام برای مقصد استفاده می‌شود؟** باید مسیر مقصد، اولویت و سیاست را بررسی کرد.
7. **Default Gateway موجود است؛ اینترنت تضمین است؟** خیر، Gateway، مسیر بالادستی و سیاست باید بررسی شوند.
8. **`nslookup` در محیط ایزوله شکست خورد؛ خطای سیستم قطعی است؟** خیر، ممکن است Resolver یا شبکهٔ مجاز وجود نداشته باشد.
9. **چرا دادهٔ خروجی را پاک‌سازی می‌کنیم؟** برای جلوگیری از افشای اطلاعات سازمانی.
10. **آیا نمونه‌های این درس خروجی واقعی‌اند؟** خیر، آموزشی و اجرا‌نشده‌اند.
11. **`netstat -rn -f inet` برای چیست؟** مشاهدهٔ مسیرهای IPv4 در macOS پشتیبان.
12. **آدرس Link-Local IPv6 به معنی اینترنت است؟** خیر، دامنهٔ آن لینک محلی است.

## واژه‌نامه و چک‌لیست

Resolver: حل‌کنندهٔ نام؛ Gateway: Next Hop مسیر؛ Prefix: طول بیت شبکه؛ Route: قاعدهٔ هدایت مقصد.

- [ ] آدرس، Prefix، مسیر و DNS را جدا می‌خوانم.
- [ ] نسخه و رابط درست را ثبت می‌کنم.
- [ ] خروجی نمونه را نتیجهٔ واقعی گزارش نمی‌کنم.
