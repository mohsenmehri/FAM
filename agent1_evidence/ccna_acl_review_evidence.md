## ۱. بررسی عمیق پاسخ‌های کوییز

### Q0: چرا در پیاده‌سازی `aaa authentication login` روی تجهیزات سیسکو توصیه می‌شود همیشه روش `local` را در انتهای دستور پس از گروه سرور قرار دهیم؟
- **پاسخ انتخاب [1]:** تا اگر سرور مرکزی TACACS+/RADIUS از دسترس خارج شد، همچنان امکان ورود با حساب اضطراری محلی وجود داشته باشد
- **توضیح:** در AAA، روش پشتیبان `local` تنها زمانی فعال می‌شود که سرورهای مرکزی پاسخ ندهند (unreachable)؛ در نبود آن، قطعی سرور AAA منجر به قفل شدن دسترسی ادمین‌ها می‌شود.
- **وضعیت:** ✅ فنی صحیح

### Q1: کدام پروتکل برای کنترل دقیق و دستوربه‌دستور دستورات CLI مدیران شبکه مناسب‌تر است و کل بدنهٔ بستهٔ خود را روی TCP رمزنگاری می‌کند؟
- **پاسخ انتخاب [2]:** TACACS+ (TCP 49)
- **توضیح:** TACACS+ روی `TCP 49` کل بدنهٔ پیام را رمزنگاری می‌کند و با تفکیک Authentication، Authorization و Accounting امکان کنترل تک‌تک دستورات CLI را فراهم می‌سازد.
- **وضعیت:** ✅ فنی صحیح

### Q2: در بررسی امنیت پیکربندی یک روتر، عبارت `enable secret 9 $9$...` نسبت به `enable password 7 ...` چه برتری بنیادینی دارد؟
- **پاسخ انتخاب [0]:** Type 9 یک Hash یک‌طرفهٔ مقاوم (scrypt) است که برگشت‌پذیر نیست، در حالی که Type 7 با ابزارهای ساده فوراً رمزگشایی می‌شود
- **توضیح:** `service password-encryption` فقط Type 7 (رمزنگاری ضعیف و برگشت‌پذیر) می‌سازد، در حالی که `enable secret` از تابع درهم‌ساز یک‌طرفه (در نسخه‌های مدرن scrypt / SHA-256) استفاده می‌کند.
- **وضعیت:** ✅ فنی صحیح

## ۲. بررسی عمیق راه‌حل تمرین‌ها

### Ex0 (ساده)
- **مهمته:** یک شرکت می‌خواهد الف) کنترل کند هر مهندس شبکه روی سوئیچ‌ها مجاز به زدن کدام دستورات CLI باشد و تمام دستوراتش لاگ شود؛ ب) دسترسی کاربران به Wi-Fi سازمانی را با ۸۰۲.۱X احراز هویت کند. برای مورد (الف) و (ب) کدام پروتکل AAA مناسب‌تر است و چرا؟
- **راه‌حل:** مورد (الف): **TACACS+ (`TCP 49`)** چون رمزنگاری کامل بدنه، جداسازی سه‌مرحله‌ای AAA و Authorization و Accounting دقیق برای تک‌تک دستورات CLI دارد. مورد (ب): **RADIUS (`UDP 1812/1813`)** چون استاندارد باز احراز هویت دسترسی شبکه (802.1X و VPN) است.
- **وضعیت:** ✅ موجود و فنی صحیح

### Ex1 (متوسط)
- **مهمته:** در بخش پیش‌نویس کانفیگ زیر ۳ اشکال امنیتی مهم وجود دارد؛ آن‌ها را پیدا کنید و نسخهٔ اصلاح‌شده را بنویسید:
`enable password Cisco123`
`service password-encryption`
`ip http server`
`line vty 0 4`
` transport input all`
` login`
- **راه‌حل:** ۱) `enable password` حتی با `service password-encryption` فقط Type 7 ضعیف می‌شود -> جایگزینی با `enable secret <StrongPass>` (بهتر: `algorithm-type scrypt`)؛ ۲) `ip http server` پنل وب رمزنگاری‌نشده را باز می‌گذارد -> غیرفعال‌سازی با `no ip http server` (و `no ip http secure-server` در صورت عدم نیاز)؛ ۳) `transport input all` یعنی Telnet باز است و `login` بدون `local` از کاربر مجزا پشتیبانی نمی‌کند -> جایگزینی با `username admin privilege 15 secret ...`، `login local` و `transport input ssh`.
- **وضعیت:** ✅ موجود و فنی صحیح

### Ex2 (چالشی)
- **مهمته:** دو روتر شعبه و مرکز یک تونل Site-to-Site IPsec VPN دارند (`QM_IDLE ACTIVE` در Phase 1 برقرار است) اما پینگ بین شبکهٔ `192.168.10.0/24` (پشت روتر مرکز) و `192.168.20.0/24` (پشت روتر شعبه) برقرار نمی‌شود و ترافیک بدون رمزنگاری از روتر خارج شده و از طرف ISP Drop می‌شود! دو خطای بسیار رایج را که دقیقاً در ترکیب **NAT + IPsec** رخ می‌دهند تحلیل کنید.
- **راه‌حل:** ۱) در بسیاری روترهای IOS، **NAT پیش از Crypto Map** اجرا می‌شود! اگر در ACL مربوط به `PAT` تمام ترافیک `192.168.10.0/24` را مجاز کرده باشیم، IP مبدأ بستهٔ رو به شعبه قبل از رسیدن به Crypto Map به IP عمومی PAT ترجمه می‌شود و دیگر با Crypto ACL هم‌خوانی ندارد! نکتهٔ مهم نحوی: برای تعریف **NAT Exemption** (که هم IP مبدأ و هم IP مقصد شعبه را چک کند) **نمی‌توان** از Standard ACL (مثل `access-list 10`) استفاده کرد؛ بلکه حتماً باید یک **Extended ACL** ساخت:
`ip access-list extended NAT_ACL`
` deny ip 192.168.10.0 0.0.0.255 192.168.20.0 0.0.0.255`
` permit ip 192.168.10.0 0.0.0.255 any`
`ip nat inside source list NAT_ACL interface Gi0/0 overload`
۲) یا عدم تطابق آینهٔ Crypto ACL در دو سر تونل برای Phase 2.
- **وضعیت:** ✅ موجود و فنی صحیح
